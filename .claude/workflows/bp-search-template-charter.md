# Search Template Epic — Charter

The epic's memory. Every wave reads this before it plans. Wave Paper (living story) per wave; this file is the durable spine.

## Vision

A stranger picks **search-starter** — from the cloud dashboard, or one command from a README that reads like a product page — and ~90 seconds later is looking at a live site that feels expensive: instant-as-you-type live search over a Phoenix websocket, a hand-written zero-dependency Canvas2D force graph breathing between densely interlinked documents, a map with no Leaflet, and every document detail page rendered pixel-perfect by the canonical `@barkpark/react` PortableDoc (all 42 block types — never the legacy `web/` fork). The seed content is rich enough that the graph is a constellation on first load. The same experience exists **per framework** (Next.js first, then Astro, then Phoenix) and **per theme** (evergreen/ember/fjord/charple), proving the claim: *Barkpark is the fastest way to something genuinely premium, without worries.*

The flagship artifact is the extraction of the web demo's finder — `web/app/(finder)/` + `finder.tsx` (1552 ln) + `graph-view.tsx` over `web/public/bp-graph.js` (3218 ln, zero-dep, zero-network Canvas2D force graph) + `listings-map.tsx` (837 ln, raw OSM tiles) + ~1650 ln of `web/lib` modules — into `templates/search-starter`, a standalone Next.js app deployable through the proven 6-stage engine to a live `/sites/<slug>/` URL.

## Decisions

- **D1 — Next.js first.** The finder is already Next code; fastest path to a launchable premium artifact. Astro (W2) and Phoenix (W3) follow.
- **D2 — search-starter is a standalone Next app, a first-of-its-kind extraction.** *Why:* place-directory (the only "landing as a template" prior art) is NOT standalone — it env-flips the shared `web/` checkout. search-starter vendors finder + graph + map + the ~11 `web/lib` modules + `bp-graph.js` into its own tree with its own `package.json`. The three demo hardcodes become config: `DOC_TYPES` (find.ts:41-49), `SCOPE "/w/default/p/default"` (find-search.ts:39), dataset `"docs"` (config.ts).
- **D3 — Runtime target is node (SSR), not static.** *Why:* the finder is Next force-dynamic; D71 proved next-starter's node-slot SSR path live, and the finder IS that shape. Rides the proven node engine.
- **D4 — PortableDoc: consume the PUBLISHED `@barkpark/react`, never vendor the renderer.** *Why:* PR #3449 is MERGED (863193ce9); `@barkpark/react` builds+tests green (185 tests) and exports a working `PortableDoc` + `paper-surface.css` subpath. Vendoring recreates the exact `web/components/portable-doc.tsx` fork the render-path epic is deleting. Detail route uses `@barkpark/react/server` + `@barkpark/react/paper-surface.css`, pinned exact `@1.0.0-preview.2` (astro-starter's `@barkpark/core@1.0.0-preview.3` exact-pin precedent).
- **D5 — npm preview.2 publish is a wave-1 human-gated PREREQUISITE, not plumbing.** *Why:* npm's live `@barkpark/react@1.0.0-preview.1` contains ZERO PortableDoc (proven by extracting the tarball). Publishing is blocked by 3 empty-frontmatter changesets that hard-fail `changeset status/version/publish`; after `git rm`ing them a preview publish cuts react preview.1→preview.2 cleanly (proven in an isolated `changeset version` run). The publish is `gh workflow run release.yml -f dist_tag=preview -f dry_run=false` on the ROOT workflow (the js/.github copies are dead files) — a human `workflow_dispatch`, NPM_TOKEN secret, pre-mode auto-applies the `preview` dist-tag. Backlog note: the pending changeset backlog is ~305 files (not 32), all folding to +1 pre-increments, no majors — a large-but-coherent changelog flush.
- **D6 — Next sub-path: bake `basePath` at BUILD time from `BARKPARK_SITE_BASE`.** *Why:* the finder is MULTI-route (`/d/[type]/[slug]`, graph-node clicks, home/bench links — all root-absolute); assetPrefix-only (next-starter's single-page fix) lets client navigation + RSC fetches escape to the domain root and 404. basePath auto-prefixes `<Link>`/`router.push`/`usePathname`/next-image, so zero href edits. Requires a NON-stripping Caddy `handle /sites/<slug>/*` branch (vs the current stripping `handle_path`) for basePath node sites + a basePath-aware health probe path (`BARKPARK_SITE_HEALTH_PATH` seam exists at site-deploy-node.sh:87-92; the Caddy-arm branch is new).
- **D7 — Launch via a NEW Provisioner template-slug axis on the LIVE engine — NOT the catalog family.** *Why:* the catalog family (catalog.go / registry.ex `@known_templates` / templates.ex `@catalog` / app_files.ex, ~9 touch points across 3 sync mechanisms) drives the `/new?template=` new-INSTANCE bootstrap + GitHub-repo-push flows, which the on-box engine never reads. The live engine (`POST /v1/admin/site-deploy` → DeployRunner → `Provisioner.template_dir/1`) selects by a hardcoded BINARY `runtime_target` switch (static→astro-starter, node→next-starter) with NO template-slug axis. W1 adds a closed-enum `template` field to `DeployRequest`, turns `template_dir/1` into a keyed lookup, wires config, and has Cloud forward `template` on the deploy payload. CLI: `bp cloud site create --template search-starter --kind node`.
- **D8 — Defer the catalog family + dashboard `/new` picker + create-site UI to Wave 2.** *Why:* W1 ships NO `templates/search-starter/barkpark.template.json` — its mere presence reds the Go `TestEmbeddedCatalogMatchesRepoRoot` reverse-drift check unless the whole 9-touch-point catalog family lands with it. "Available when creating a site in the dashboard" is itself a bigger gap: the authenticated in-dashboard create-site UI does not exist (the SPA has NO `POST /v1/sites`; site creation is CLI-only). W1 delivers CLI-launchable + a live URL; W2 does dashboard availability + the manifest + the catalog feed.
- **D9 — Manifest schema widen (framework enum + theme field) moves to Wave 2.** *Why:* no W1 consumer (W1 ships no manifest) and it is land-order-coupled to the catalog family; YAGNI here. Widening `barkpark.template.schema.json`'s `["nextjs"]` enum + adding an optional `theme` field pairs with W2's manifest.
- **D10 — Rich interlinked SINGLE-TYPE seed corpus, mutations format.** *Why:* bootstrap.go publishes exactly ONE type per seed and rolls back the WHOLE batch on any type mismatch (proven via `mutate_test.exs:23`), and refuses ndjson/script formats. So the corpus is one content type self-referencing via a scalar `reference` field AND an `arrayOf`-of-`reference` field (both edge-extracted today), values = bare sibling doc_ids present in the same file (a dangling ref → phantom node), all docs published (graph reads `:published` only). Multi-type (posts↔authors↔categories) needs a bootstrap.go/template.go per-doc-`_type` extension → backlog. Net-new authoring: no template ships reference-populated seeds today.
- **D11 — Graph theme parity is a two-part fix that touches bp-graph.js.** *Why:* `graph-view.tsx:139 theme:"dark"` is a LIVE bug, and bp-graph.js's `"auto"` resolves via `matchMedia` ONLY (never reads the DOM), so it diverges from the site's real `document.documentElement.dataset.theme` whenever a user toggles against OS preference. Fix: graph-view reads `dataset.theme` + subscribes to the existing `bp:themechange` event; bp-graph.js gains a `setTheme` on its controller (theme is a closure var flowing to paint helpers) for live re-skin without destroy/recreate. The template's own graph-view is born correct.
- **D12 — The template's vendored bp-graph.js is a deliberate one-time SNAPSHOT, not byte-locked to web/api.** *Why:* the existing 2-copy byte-identity pact (web/public + api/priv/static) is discipline-only; a third byte-locked copy is friction. W1 adds a `templates/**` trigger to `doc-gates.yml` so template CSS/theme PRs at least RUN the design gate (today they never trigger it — proven: zero `templates/**` in the paths list). A byte-identity CI tripwire for the template graph copy is backlog hardening.
- **D13 — Transport: co-located rides `/v1/local/search` loopback; the D29 public-read token satisfies WS + graph.** *Why:* proven — a public-read site token passes UserSocket connect + SearchChannel join (`permits?(:read)` true, membership minted at create) AND the flat `/v1/graph` route (require_token, no PublicRead clamp on that pipeline). **CONSTRAINT:** flat `/v1/graph` resolves the DEFAULT workspace via `AssignDefaultScope` and IGNORES the token's bound workspace — there is no scoped `/w/:ws/p/:proj/v1/graph`. So the seed corpus MUST live in the site's Default workspace or the graph renders empty while search works. A workspace-scoped graph route is backlog.
- **D14 — README is honest marketing; the install-cli 404 is STALE.** *Why:* live `curl … install-cli.sh | sh` installs bp 1.15.0 (fix #2797) and `bp login --device` shipped. The one command is `bp cloud site create --template search-starter` → the proven 6-stage engine (BPSTAGE-streamed, D25) → live `/sites/<slug>/`, NOT `bp-vercel-quick-setup.sh` (operator script) and NOT the dashboard (deferred). This README sets the standard the 0-byte blog/website starter READMEs will retrofit.

### Wave 6 decisions (D29–D36) — an in-flight site build survives a box restart

- **D29 — Survival = the WHOLE engine script as a `systemd-run` TRANSIENT UNIT, not just the build.** *Why (proven on guerrilla):* today's inner `systemd-run --scope` ALREADY orphans npm into a surviving SIBLING cgroup — the build already survives a slot restart; what DIES is the orchestrating script (a BEAM `Port.open` child sitting in the slot's `KillMode=control-group` cgroup). So DeployRunner launches `bash deploy/site-deploy.sh` ITSELF as `systemd-run --unit=bp-site-build-<slug>-<buildid>` (sibling cgroup, unaffected by the parent unit's control-group kill), which holds the per-slug flock and drives PLAN→…→RETIRE to completion detached. The inner build `--scope` is REMOVED; the transient unit carries `-p MemoryMax=1500M -p CPUQuota=150%`. A design that wraps only npm changes NOTHING vs today.
- **D30 — The acceptance target is the SLOT unit, NOT `barkpark.service`.** *Why (proven):* `systemctl is-active barkpark.service` → `inactive` on guerrilla; the live kill is the blue/green retire (`systemctl disable --now barkpark-slot@$OTHER`, near-immediate control-group kill). The LIVE acceptance restarts `barkpark-slot@<active>` mid-BUILD with a deliberately SLOW build — every observed real build finishes in 10–30s, so a sleep-padded/large-corpus build is required to exercise the true mid-BUILD window.
- **D31 — Durable seam is a FILE CONTRACT, never journalctl.** *Why (greenfield — DeployRunner is 100% in-memory, init resets to empty maps):* DeployRunner writes a per-run `manifest` `{slug, build_id, mode, runtime_target, unit_name, status_file, log_file, build_env_file, started_at}` at spawn; the engine dual-sinks each BPSTAGE line to stdout AND `$BARKPARK_SITE_STATUS_FILE`, and tees raw build stdout/stderr to `$BARKPARK_SITE_LOG_FILE` — a real PERSISTENT file (not the deleted `mktemp`, not a `tee`-pipe rooted in the dying cgroup, which SIGPIPE-kills an orphan). The log file MUST carry RAW child output: `reason_tail` rejects BPSTAGE lines, so a marker-only file degrades every failure to a bare `exit_label`.
- **D32 — DeployRunner becomes observer+finalizer; `init/1` re-attaches.** *Why:* `status(slug)` reconstructs the run map from manifest+status+log — stage fold is first-seen ORDER / latest-status-wins / RAW engine tokens (`started|ok|skipped|noop|failed`; the CP does the `ok→done` mapping, so NEVER serve `done` before the fold is populated or the CP settles the site live to a build that never finished). `init/1` scans the run dir, checks each unit's liveness (`systemctl is-active <unit_name>`), re-attaches a live unit as `:running` (re-arming the deadline) and repopulates single-flight so a re-trigger 409s instead of flock-queueing a second engine. `$BARKPARK_SITE_STATUS_FILE` unset (dev/selftest standalone) ⇒ the engine keeps stdout-only behavior, backward compatible.
- **D33 — Env hygiene: `EnvironmentFile=` (0600), NEVER `--setenv`/argv.** *Why (proven on guerrilla):* `--setenv=K=V` leaks the VALUE via `systemctl show -p Environment`; `EnvironmentFile=` shows only the path. Today's `systemd-run --scope … env -i BARKPARK_TOKEN=… npm build` ALREADY leaks the live token in the journal scope description — a shipping ride-along fix. DeployRunner writes a per-run 0600 `build_env_file` (modeled on `write_slot_env`, unlinked after the run) passed as `-p EnvironmentFile=`; the engine's inner build reads secrets from its inherited environment, never re-injecting them on argv.
- **D34 — `build_id` becomes a first-class match key, box-side, CP normalizer UNCHANGED.** *Why:* today `status/2` reads only `slug`, so a second run for the same slug silently has its stages adopted by a CP polling the first `build_id`. Purely controller-side: read the `build_id` query param (BoxRelay already sends it); if present, non-empty, and ≠ the served run's `build_id` (or the run is idle), respond **404** — the CP already treats 404 as "keep waiting", so a superseded/not-yet-started build times out honestly instead of adopting another run's success. Empty (rollback `await_flip` sends `""`) or absent (legacy) → slug-only, backward compatible.
- **D35 — CP bounded restart-grace in the poll loop is MANDATORY (REFUTES the direction's "CP relay poll unchanged").** *Why (proven, two scouts + a throwaway probe):* `poll/2` terminal-fails on the FIRST `{:error,_}` (deploy.ex:407-408), and a failed row is permanently unresurrectable (no failed→live edge, not re-claimable, the reaper never touches failed) — so a slot restart marks the Deployment failed ~2s in and box survival ALONE cannot meet the acceptance criterion. Add a bounded consecutive-error grace BEFORE `fail()`: a SEPARATE counter (NEVER share `left`) that RESETS on any successful 2xx/404 poll, ~60–90s (e.g. 45 error-polls × 2s). Poll-loop-only — NOT `start_on_box` (`sites_deploy_test.exs:394` stays green; a box that never accepted the build still fast-fails). `settle_live` double-fire is safe (idempotent same-status write; failed terminal). New permanent tests: grace-resume + grace-exhaustion. Prod runs the 900s poll budget / 900s reaper clock unoverridden.
- **D36 — Re-attach selftest coverage rides the OFFLINE faked/fallback path; systemd is proven ONLY live.** *Why:* both engine selftests (87 + 76, gate FAILS==0 not exact counts) grow a kill-and-reinvoke re-attach case over the file contract (write manifest+status+log, kill mid-BUILD, re-read/reconstruct with zero live process). macOS is bash 3.2 with no `setsid`/`systemd-run` (all already faked) — the fake long-build driver must be a SEPARATE script file or have its pid captured by the caller's `$!` (never self-reported via `$$` inside a backgrounded function — wrong under bash 3.2). `systemd-run --unit` production behavior is proven ONLY by the live guerrilla acceptance run. Supersedes duplicate task `site-spawner-deploy-run-state-survives-beam-restart` (#3206).

### Wave 7 decisions (D37–D48) — THE finder on the Astro flagship (dual-engine parity by identity)

The user's "big thing": the Astro Search template must work EXACTLY like the Next Search template — the dual-engine (indx typo-tolerant + Postgres FTS) per-keystroke finder — on the statically-deployed Astro flagship. Verified with two rounds of live ground truth on guerrilla; several decisions REFUTE the pre-Decide direction. Templates-only, **Elixir-exempt, zero api/.ex touch (D47)**. Paper: `search-template-wave-7-2026-07-17`; task: `stw7-astro-finder-parity` (p0, USER DIRECTIVE).

- **D37 — Postgres leg + telemetry ride the FLAT ANONYMOUS route, ZERO token.** *Why (proven live, REFUTES the charter's scoped-route+public-token direction):* `GET /v1/data/search/:dataset` (flat, no `/w/:ws/p/:proj/` prefix) served BOTH `engine=postgres` and `engine=indx` to a fully anonymous caller (no Authorization header) — HTTP 200, real hits, published-only (`AnonPerspective` floors tokenless callers; `?perspective=drafts` returned identical count, NO leak — proven by 3 independent verifiers). The SCOPED route the charter named 403s anonymous AND carries a CONFIRMED SEVERE draft-exfiltration leak (a public-read token + `?perspective=drafts` returned 206 draft docs, 100 in-page, spanning book/mediaAsset/paper/sheet/tag/task). So flat-anonymous is the biggest available simplification: nothing embedded in the bundle for postgres, no CORS decision (same-origin), no clamp-gap. Telemetry rides the same flat-anonymous `/{interaction,correction}` (proven `{ok:true}` anonymous) with `X-BP-SEARCH-CLIENT: <sid>` — ON by default (finder parity), never a token.
- **D38 — Indx/live leg rides the WS SearchChannel (BOTH engines via the `engine` param), reusing the deploy-minted `BARKPARK_TOKEN` (public-read), WS_URL derived from `new URL(BARKPARK_API_URL).origin + "/socket"`.** *Why (proven live):* a minted public-read token joins `search:default:default:production` and both engines return non-empty `documents[]` (indx 100/142, postgres 100/142; browse 100/278). The channel requires a real `:read`-authorized token to join (empty token can never join). The deploy engine ALREADY mints a public-read token and bakes it as `BARKPARK_TOKEN` (`mint_public_read_token` → `permissions:["public-read"]`); the WS URL derives from the API origin. NO new env var, NO api/.ex change — matches the Next template's existing WS token model exactly (parity, not new exposure; D13 already accepts this token reaching the browser for graph).
- **D39 — Live per-keystroke path is the WS channel for BOTH engines; the HTTP `/api/find` path (fallback + suggestions + telemetry) is served browser-direct via a fetch INTERCEPTOR installed by the island — finder.tsx stays BYTE-IDENTICAL.** *Why (source-confirmed):* `finder.tsx:645` is a ternary — `ready ? liveSearch(...) : fetch(apiPath("/api/find?..."))`; `useLiveSearch` pushes `push("query",{q,engine,...})` so the WS channel carries BOTH engines by the `engine` param. `/api/find` (fallback), `/api/find?suggest=1` (always HTTP), and `/api/find-event` (telemetry) have no server on a static host. The param contract differs (`/api/find` injects `types`/`perspective`/`limit` server-side), so a URL rewrite is insufficient — the island installs a `window.fetch` interceptor that translates these three routes to the flat-anonymous barkpark routes and shapes the reply via the isomorphic `shapeFindResponse` (already in the closure). finder.tsx is vendored verbatim; the interceptor is new glue, analogous to the nav shim.
- **D40 — Browse/prefix seed baked at BUILD as a static `search-seed.json` (graph.json pattern); `allDocs()` is the seed source.** *Why (proven):* ranked-browse (`engine=indx`, `q=" "`) order == `_updatedAt:desc` listing order (pairwise concordance 1.0000, 0 rank delta, two runs), so the bake step's API choice is a wash for ordering — `allDocs()` (`.order('_updatedAt:desc')`, one call, already in `bp.ts`) is the source. Mirror `graph.json.ts`: a build-time endpoint serializes the seed; the island runtime-fetches it (like GraphIsland fetches graph.json), degrading gracefully if absent (empty seed, finder still works).
- **D41 — Mount variant `page`, NOT `master`.** *Why (opus verify):* the master-split needs Next's persistent nested App-Router layout (the `<Finder>` lives in the layout, only `children` swaps) — impossible on a static host where every navigation is a full page load and the finder MUST remount. Replicating it = a full SPA client router = violates the thin-adapter doctrine + bloats the wave. The finder's ENTIRE search state is URL-derived (q/engine/sort/facets from `useSearchParams`), so a page-variant remount reconstructs the exact search view — the SEARCH experience (the user's wish) is 100% preserved. What's lost is the split-view SHELL (read-doc-alongside-search, zero-reload open), NOT the finder. Named honestly: `page` is the retired standalone branch of the same file (once shipped), the correct static-host target — NOT byte-identical to today's live master-split.
- **D42 — `next/link` + `next/navigation` shimmed via Vite alias (2 ~30-line modules over `<a href>` + window.location/history/popstate); finder.tsx + the 13-module closure vendored VERBATIM.** *Why (finder-trial-build PASSED GREEN):* the closure is finder.tsx (1552 ln) + exactly 13 lib modules (find, find-shape, config, hovered-doc-context, finder-nav-context, use-live-search, prefix-seed, did-you-mean, search-session, stem, fuzzy, tokens.gen, base-path) — self-contained, no 14th dep.
