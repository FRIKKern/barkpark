# Epic charter — API read-path security sweep: the ShareLink raw-token cross-tenant leak

Epic task: `api-read-path-security-sweep`
Wave Paper: `api-read-path-security-sweep-wave-share-link-raw-token-2026-08-18`
Wave referent: `arpss-w8-sharelink-wave-1-log`
Audited against origin/main `5cd2e0ad08941313544cd636485e79791e723d08`.

## Vision

Close the second half of the share-surface tenancy leak on the SAME predicate the first half just landed, and leave behind something more durable than three patches: a written denial-shape law that keys on WHERE a name arrives in the request rather than on which verb was called.

The confirmed defect, re-derived on origin/main and unchanged by the merge of the sibling half: `BarkparkWeb.ShareLinkController` (`api/lib/barkpark_web/controllers/share_link_controller.ex`) has exactly FOUR actions — `show:29`, `mint:168`, `list:206`, `revoke:219`. There is no `rotate`/re-issue action; the wish's premise on that point is REFUTED and the charter records it so no future wave hunts for one. All three ADMIN actions sit behind a `:require_admin` plug that proves a GLOBAL permission bit and never reads a workspace, and all three resolve their target from client input:

- `list` resolves the workspace from `Tenancy.get_workspace_by_slug(params["scope"])` at `:208`, then maps every row through `link_json/1` at `:211`, and `link_json` emits `url: l.token && share_url(l.token)` at `:304`. `Sharing.Links.create/1` persists the PLAINTEXT token beside its hash, so a listed foreign row is a LIVE CREDENTIAL in a stranger's response body. This is credential disclosure, not metadata leakage.
- `mint` is a CO-CROWN, ranked above the wish's ranking: it validates `ensure_item_exists` against the FOREIGN scope (already an existence oracle on another tenant's content) and then mints a real link — `access: "edit"` is accepted — INTO workspace B, returning the raw token. Reading B's existing tokens is bounded by what B already shared; manufacturing a new edit credential in B is unbounded, persistent, and invisible to B's admins.
- `revoke` reaches a bare `Repo.get(ShareLink, uuid)` with no scope at all. Cross-tenant write.
- `show` (`GET /s/:token`, browser pipe) is DELIBERATELY UNCHANGED — the token IS the authorization. An enumeration that silently omits the public reader is how a fix wave ships a regression, so its untouched disposition is on the record.

Honest severity, stated rather than inflated: the routes sit behind `:require_admin`, so the attacker IS an admin. No shipped HTTP endpoint mints the `admin` bit — six controllers cap below it (`token_controller` `~w(public-read read)`, `app_token_controller` `~w(read write chat)`, `auth_controller` hardcodes `["read"]`, `playground` `["read","write"]`, `fleet_support` `~w(read write)`), and it is born only in the install and demo seeds. On Cloud, one team owns one instance (`cloud/.../registry/barkpark.ex:305` `belongs_to :team`), so no co-tenant exists to leak to. But co-tenancy on a shared self-hosted install is SELF-SERVICE (`POST /api/workspaces`, any authenticated token becomes owner), and `auth.ex:471-480` already implements the role-gated admin-PAT mint whose only caller hardcodes `["read"]`. The exploit precondition is ONE product feature away, and the feature is already half-built. We fix the boundary.

Fence: `api/lib/barkpark_web/controllers/share_link_controller.ex` + `api/lib/barkpark/sharing/` + FOUR test files (`api/test/barkpark_web/controllers/share_link_test.exs`, `api/test/barkpark_web/controllers/share_token_controller_test.exs`, `api/test/barkpark_web/contract/pds_delete_receipt_differential_test.exs`, `api/test/barkpark_web/integration/http_cache_policy_test.exs`) ONLY. NO `barkpark_web/live`, no `share_controller.ex`, no shared-helper refactors, no `content/`, `search/`, `media/`, `cloud/`, `js/`, `web/`.

## Decisions

- **D1 (DISPOSITION, and it REVERSES a verifier recommendation) — SUPERSEDE #12404: the lead CLOSES it BEFORE the replacement PR opens, and the wave builds on a fresh branch off clean origin/main.** Why: the verifier recommended rework-in-place on #12404's branch, reasoning from a board where #12519 was still open and #12405 still live; that board has since MOVED — measured now, `gh pr view` says #12519 is **MERGED** (`71315ef23e`, 2026-08-18T22:09:12Z) and #12405 is **CLOSED**. The sibling half's own resolution was therefore supersede-and-close, not rework, and mirroring the sibling means mirroring its disposition too. Closing #12404 first also fully retires the verifier's real objection (main's merge queue is non-strict, so two green PRs on the same five hunks land a mixed predicate) without pushing to another wave's builder branch uninvited (Heggemsnes Act). The fixture-repair line from #12404 is re-imported by reference, not rediscovered.
- **D2 (PREDICATE, not re-litigated) — MEMBERSHIP in the TARGET workspace via `Tenancy.Auth.workspace_admin?/2`, reached through a local private total-ising wrapper mirrored VERBATIM from the now-merged `share_controller.ex:269-292`.** Why: it is the repo's canonical grant chokepoint (`@canonical capability:workspace-admin-authority`, `tenancy/auth.ex:337`) and its own docstring names the exact gap both proofs are written against. `authorize/3` is BANNED and the ban is now MEASURED, not argued: on the leak fixture `authorize(tok, B, :admin)` returns `:ok` while `workspace_admin?(tok, B)` returns `false`. The predicate now lives on main, so the mirror is a copy of merged code — the "predicate drift from copying an unmerged private helper" attack is retired.
- **D3 (TOTALITY) — the wrapper needs THREE guards plus a catch-all clause, and every one is load-bearing.** Why: mutation-measured, not read. Bare `workspace_admin?/2` RAISES on five of seven inputs — `FunctionClauseError` on nil actor / `%CallerContext{}` / `%ApiToken{id: nil}` / nil ws, and **`Ecto.Query.CastError`** (NOT the `Ecto.CastError` that `repo.ex`'s own docstring names — a doc defect, filed) on `""` and any non-UUID. Deleting the catch-all reds the three actor shapes; deleting the ws guard reds the three ws shapes; deleting the token-id guard reds `%ApiToken{id: nil}`. The actor is read as `conn.assigns[:api_token]` SPECIFICALLY, never a generic principal helper — `CallerContext.from_conn/1` prefers `:caller_context` and that shape raises.
- **D4 (PLACEMENT, run-proven, and one line late ships an oracle) — the gate goes IMMEDIATELY after `Tenancy.get_workspace_by_slug/1` and BEFORE `Tenancy.get_project/2`.** Why: measured at three placements. Gate AFTER `get_project`: an existing project slug in B answers 403 while a nonexistent one answers 422 — project-slug enumeration SURVIVES the patch. Gate AFTER `ensure_item_exists`: existing item 403 vs missing item 422 — the item-existence oracle survives the denial. Gate BEFORE `get_project`: all three collapse to 403. Stated at full strength, the early placement closes the item-existence oracle in BOTH its 422 and its **201** forms — the 201 being the loudest positive answer and the co-crown leak itself.
- **D5 (THE TRAP THAT SILENTLY VOIDS THE FIX) — the denial term must be NON-BINARY (`{:error, :forbidden}`) AND both `mint` and `list` need an EXPLICIT `{:error, :forbidden} -> forbidden(conn)` else-arm.** Why: demonstrated, not predicted. `mint`'s existing else carries `{:error, msg} when is_binary(msg) -> unprocessable(conn, msg)` and `list`'s else is a bare `_ ->` catch-all, so a gate returning a string is SWALLOWED into 422 and a bare atom tuple falls to the catch-all — also 422. A probe gate returning `{:error, "PROBE-DENIED"}` produced `422 validation_failed`, not 403. Without the explicit arm the entire denial-shape law collapses into the pre-existing 422 on both admin actions.
- **D6 (THE DENIAL-SHAPE LAW — the wave's most portable output) — THE SHAPE FOLLOWS THE INPUT, NOT THE VERB, and the discriminant is WHERE THE NAME ARRIVES.** Why: the direction's first phrasing ("nonexistent tenant slug → 422") is FALSE as a general law and would be refuted by the first grep — `ResolveWorkspace:76` and `WorkspaceController:85,117,185` both 404 an unknown slug. Re-keyed on arrival position it covers every JSON `/v1` surface with no exception:

  | Input class | Example on this surface | Shape |
  |---|---|---|
  | PATH-ADDRESS slug, unknown | `/w/:workspace_slug/...` | 404 (`resolve_workspace.ex:76`) |
  | PATH-ADDRESS slug, exists, no authority | same | 403 (`resolve_workspace.ex:134`, `require_workspace_role.ex:30`) |
  | PAYLOAD/QUERY value, unresolvable | `?scope=ghost-ws/...` | 422 UNCHANGED — no tenant to confine to |
  | PAYLOAD/QUERY value, exists, no authority | `?scope=<real foreign ws>/...` | **403** (`list`, `mint`) |
  | OPAQUE ROW ID, foreign tenant | `DELETE /v1/shares/links/:id` | **404 byte-identical to a missing row** |
  | id non-castable or nil | `.../not-a-uuid` | DENIAL, never 500 |
  | no named target | (unreachable here — `list` requires a scope) | 200, foreign rows simply absent |

  ACCEPTED SIGNAL, recorded rather than hidden: even at the early placement a caller still distinguishes an EXISTING foreign workspace (403) from a nonexistent slug (422). That is the unavoidable consequence of the resolve-first/authorize-second ordering the sibling half established and reviewed; checking edit-shared first would leak the foreign share CONFIG, which is strictly worse. It is a workspace-slug oracle only, never a contents oracle. The law must carry the reasoning at the site, or the next auditor "fixes" it into a leak.
- **D7 (BYTE-IDENTITY IS AN INSTRUCTION, NOT AN ASSERTION) — the foreign-row denial calls the SAME `not_found_json(conn, "link not found")`, and the 403 mirrors the sibling's `ErrorResponse.emit(conn, {:error, :forbidden}, "workspace access required")`.** Why: evaluated against the compiled build, both 404 envelopes are `%{code: "not_found", message: "link not found", hint: "Check the document _id..."}` with `IDENTICAL: true` and key set `[:code, :message, :hint]` — no `details`, and `request_id` is per-REQUEST so it cannot discriminate. Byte-identity is therefore a property of REUSING ONE CALL SITE, not something to assert about the framework; a hand-rolled `json(%{error: ...})` breaks it three ways at once. Two non-body discriminants stay OPEN and are stated rather than implied away: response HEADERS (deny inside the same action, after the same plugs) and TIMING (the foreign path runs one extra membership query).
- **D8 (THE FENCE IS FOUR TEST FILES, NOT TWO — the wish's gate command produces a VACUOUS GREEN)** — `pds_delete_receipt_differential_test.exs:245` and `http_cache_policy_test.exs:198` BOTH red under the MEMBERSHIP predicate, run-measured (30 tests, 11 failures with the gate on). Why: neither is a contract break; both are FIXTURE ARTIFACTS. `Auth.create_token/5` resolves `workspace_id || default_workspace_id()` and writes the home membership in the RESOLVED workspace, so a `create_token/4` admin lands in `default` while the link's target is a bare `create_workspace!` fixture that writes NO membership (`tenancy_fixtures.ex:46`). A builder who runs only the two files the wish names ships green and breaks main.
- **D9 (FIXTURE REPAIR IS STEP ONE, BEFORE THE GATE) — one `Tenancy.Auth.create_membership(ws.id, admin_tok.id, "admin")` per file, three files.** Why: with the fixture unrepaired the gate looks catastrophic and the honest signal drowns — 8-9 of `share_link_test.exs`'s tests red at once (measured 8 with a list+mint gate, 9 with a list+mint+revoke gate), and 7-8 of them are `/s/:token` RENDER tests with nothing to do with tenancy. Repaired first, the same gate runs 30 tests / 0 failures across all four files. `create_membership/4` is public, defaults `principal_type` to `"api_token"`, and is the same call `insert_token_with_membership/3` makes internally — no production change is needed for either cross-file suite. In `pds_delete_receipt_differential_test.exs` return the token struct from `setup` as context; do NOT recover it with `Barkpark.Auth.verify_token/1` (green but a reviewer will correctly flag the indirection). The `"minting a link for a non-existent item is 422"` test is the ORDERING CANARY: repaired, it returns to 422, proving the gate pre-empts the pre-existing contract only for an actor who is not an admin of the target.
- **D10 (THE LEAK PROOF ASSERTS ON THE BODY, REFUTES FIRST, STATUS LAST, WITH A POSITIVE CONTROL IN THE SAME FILE)** — `refute body =~ raw_token` then `refute body =~ "/s/"` then `assert resp.status == 403`. Why: assertion ORDER is load-bearing and both orderings were run. With the status assert first, the mutation reds on the status and NEVER demonstrates the body leak — the test would look mutation-verified while proving the weaker claim. With the refutes first, the mutation reds showing the foreign workspace's live token verbatim in the JSON: `"url":"http://192.168.1.142:4000/s/XGJe6EfCgBVnn4LHOO71ehNA_bG5MHZt"`. And a refute-only test aimed at a nonexistent scope PASSES on the LEAKING controller (measured: 1 test, 0 failures) — refutes alone are green on any denial, so the positive control (the legitimate own-workspace 200 body DOES contain the token) is what makes them mean anything. Assert on the raw token and the bare `"/s/"` ONLY, never a host prefix: `share_link_base()` returned the LAN IP locally and is nil in a CI container.
- **D11 (THE SPECIMEN STAYS, NAMED) — `share_link_test.exs:431-443` "list shows an item's links (no token/hash)" is left in place and cited as this wave's own failure mode.** Why: it refutes two absent MAP KEYS and passes today on the leaking code because the secret rides in `url`. It is a true statement about keys and a false suggestion in its name, sitting in the very file this wave edits. Naming it teaches more than deleting it; the new pair carries the real claim.
- **D12 (THE HOST-ADMIN PROOF IS PERMISSIVE AND MUST BE MUTATION-VERIFIED AGAINST OVER-CONFINEMENT, NEVER REVERSION)** — build the actor the way a real install builds one (`Auth.create_token/5` → `insert_token_with_membership/3`), NEVER a hand-inserted `%ApiToken{workspace_id: nil}`; then red it by raising the role floor to `owner` and by refusing to honour a Default-workspace membership. Why: a permissive assertion structurally cannot red under a full reversion — the sibling half measured this and recorded it as an HONEST LIMIT. Calling it mutation-verified without the over-confinement pair would be a stamped, hollow proof.
- **D13 (THE LIVEVIEW TWIN STAYS OPEN, AND THE PAPER SAYS SO) — `item_share.ex:69` is NOT closed by this wave, and `arpss-item-share-revoke-unscoped-revoke` is UN-SUBSUMED.** Why: the chain is verified live on origin/main — `Caps.admin?/1`'s token arm is documented membership-FREE ("an `admin`-permissioned api_token is admin wherever it is", `caps.ex:239-242`), the handler never reads `current_workspace` (its only reference is line 49, inside `item_share_create`), and it passes the raw `phx-value-id` to the unscoped `Links.revoke/1`. `studio_live_shares_test.exs` stayed GREEN under the controller gate — positive evidence the LiveView arm is untouched by a controller-only fix. Its task carries a stale "SUBSUMED BY SA-S1 … do NOT dispatch separately" header; leaving that in place while superseding #12404 would let a later close silently close a live IDOR.
- **D14 (LEDGER REPAIR IS PART OF THE WAVE, NOT AFTERCARE)** — `arpss-w8-rework-12404-onto-membership`'s criterion "both cross-file tests pass UNMODIFIED under the new predicate" is PROVEN UNSATISFIABLE (both files are fixture artifacts under EITHER predicate) and its whole roster was rewritten to permit fixture repair; `arpss-share-link-object-authz-close` is CANCELLED as superseded, with each of its eight `met=true` criteria carrying an inline RETRACTED annotation naming the banned shape. Why: an honest builder facing an impossible criterion either fails it or fakes it, and no build gate catches a ledger that permanently records a rejected shape as met. MECHANISM NOTE, worth keeping because it is correct behaviour and will surprise the next wave: a stamped `met: true` CANNOT be cleared by patching the draft and publishing — the server refuses with `stale draft: publishing this draft would clear the met: true flag ... a stamp is written DIRECTLY to the published row and never rebases an open draft`. So the retraction rides ON the evidence string and the slice is closed through the sanctioned verb (`bp task close ... cancelled`) rather than erased. That guard is a feature: proofs are not silently unstampable.
- **D15 (BUILDER MODEL IS opus@medium DESPITE HIGH-FLIP)** — Fable is capped until Aug 21 by standing order. Why: mitigated by a brief that carries every measured trap (D3-D5, D9, D10), by the fact that the predicate and its wrapper are now COPIED FROM MERGED MAIN rather than designed, and by D16.
- **D16 (HIGH-FLIP-RISK: credential disclosure + a tenancy predicate) — an INDEPENDENT second reviewer re-derives BOTH proofs before the lead merges.** Why: the single wave-reviewer re-reading the builder's reasoning is not independence; the escape this wave exists to close is exactly the kind a first reviewer confirms rather than tests. Dispatching that second reviewer is a MANUAL LEAD STEP.
- **D17 (DIRECTIONS B AND C ARE FILED, NOT BUILT)** — B (push the predicate into `Barkpark.Sharing.Links`) is architecturally the better home but `Links.revoke/1` has a non-HTTP LiveView caller with a socket actor, not a conn, so a signature change ripples outside the fence. C (stop emitting the raw token from `link_json` entirely) kills the disclosure CLASS independent of tenancy and is the strongest thing said against the winner — but the stable re-copyable `/s/<token>` URL is a deliberate P7 feature with its tradeoff argued in `20260609150000_add_token_to_share_links.exs`, killing it is a breaking API change this wave has no mandate for, and it leaves mint and revoke wide open. Both are real merit, filed with their reasons.
- **D18 (THE ADVISORY FORMAT RED IS INHERITED FROM MAIN — DO NOT "FIX" IT)** — three test files (`compose_test.exs`, `media_synonyms_scoping_test.exs`, `search_synonyms_scoping_test.exs`) are unformatted on origin/main itself and fail `mix format --check-formatted` on every branch cut from it. Why: touching them breaches the fence, and a reviewer who misreads the red as ours will ask for exactly that.
- **D19 (ONE IN-FENCE DOC DEFECT IS CORRECTED)** — `share_link.ex:6-7` asserts "The raw token is never stored — only its SHA256" sixteen lines above `field :token, :string`. Why: an auditor reading that moduledoc down would conclude this disclosure is impossible. Zero behaviour, two lines, inside the fence.
