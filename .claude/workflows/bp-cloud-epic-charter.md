# Epic charter — Tenancy-auth totality: making the authority chokepoint deny instead of crash

Epic task: `api-read-path-security-sweep`
Wave Paper: `tenancy-auth-totality-wave-2026-08-19`
Wave referent: `api-read-path-security-sweep-wave-9-log`
Audited against origin/main `bf499f54b63135b8ae078305b83f2b5b2c078877`.

## Vision

`Barkpark.Tenancy.Auth` is the declared tenant-authority chokepoint — `workspace_admin?/2` even carries the workspace-admin-authority canonical marker — and its moduledoc says, in as many words, "It is total: any non-member, unknown action, or unrecognised principal is denied." That sentence is a phantom warrant, and it has been cited six times.

The module is total on SHAPE and not on VALUE. `membership/2` has three heads and no catch-all; its `%ApiToken{}` head carries no guard at all and simply delegates, so the raise surfaces one hop deeper than any reader expects. A `nil` or non-binary id in either position raises `FunctionClauseError`; a binary-but-non-castable id — the empty string included, which is the shape a client-supplied `?workspace_id=` most plausibly produces — raises `Ecto.Query.CastError` from the `:binary_id` comparison inside `Repo.one`. `membership_role/2`, `member?/2`, `workspace_admin?/2` and `authorize/3` all inherit it. `authorize/3`'s trailing catch-all does not save it: the `%ApiToken{}` arm guards only `is_binary(workspace_id)`, so `""` satisfies the guard, matches the arm, reaches the query and raises — the catch-all never runs.

A raise on an authorization path is a crash where a denial belongs, and the status split is itself an information channel. This wave makes the chokepoint fail CLOSED, changes NO authorization semantics, and states every caller's crash-reachability.

The evidence that the chokepoint is not doing its job is already sitting in the repo: two separate waves (#12519 `share_controller`, #12569 `share_link_controller`) each hand-rolled the same ~6-line wrapper routing ids through `Repo.uuid_or_nil/1` before calling in, and `barkpark_web/studio/caps.ex` independently hand-wrote a third. Three re-implementations past a marked chokepoint is what a missing invariant looks like. The finished experience is that the next share-controller-shaped wave writes `TenancyAuth.workspace_admin?(actor, ws_id)` and stops.

The census that made this decidable: **58 real call sites across 32 modules** in `api/lib` — the wish estimated ~10, the strategic direction 24, and four prior counts disagreed because they counted syntactic hits rather than call sites and missed the bare-`Auth.` aliased form entirely. Of those, 56 are GUARDED (mostly by resolved-struct provenance — the workspace id is a loaded `%Workspace{}.id`, never a raw param) and **2 are genuine REACHABLE-CRASHES**, both at `/v1/access`, both reachable by the weakest possible principal, and both healed transitively by the seam without a caller edit.

## Decisions

**D1 — One normalisation seam inside `membership/2`, not four patched entry points.** *Why:* all five read entry points funnel through `membership/2`, so totalising it makes `membership_role/2`, `member?/2`, `workspace_admin?/2` and `authorize/3` total for free — and a clause-by-clause patch would encode no rule that keeps the SIXTH entry point safe, which is the hand-rolled-wrapper disease relocated one level inward.

**D2 — THE SEAM IS ASYMMETRIC, and this is the single most consequential ruling in the wave.** *Why:* `member?/2`, `membership_role/2` and `workspace_admin?/2` each have exactly ONE clause taking bare unguarded variables, so a trailing denial clause on any of them is a COMPILE FAILURE (`this clause cannot match because a previous clause always matches`) that the required Elixir gate turns into exit 1 — verified by mutation. Only `membership/2` can take a terminal arm; the other three get zero edits and are total by delegation. A builder who writes four symmetric clauses reds the gate on the first push.

**D3 — The cast guard goes on `db_actions/2` and NOWHERE higher; `role_permits?/3` and `granted_actions/2` stay byte-identical.** *Why:* `role_permits?("admin", "", :admin)` returns TRUE today because `granted_actions/2` resolves built-in role names from the compiled-in map before any DB read, deliberately workspace-id-independently so a tenant can never redefine `admin` to escalate. A guard placed before that lookup flips four rows `true -> false` — a silent authorization TIGHTENING, the one thing this wave must never do — and zero existing tests would have caught it. Only a CUSTOM role name reaches the DB and raises.

**D4 — `role_permits?/3` is EXCLUDED from the malformed matrix and gets its own three-row test with a SPLIT expectation.** *Why:* a self-extending table that enumerates public arity-3 predicates would assert `role_permits?("admin","",:admin) == false` and thereby FORCE the tightening D3 forbids, under a green suite; its first argument is a role string, not a principal id, so the malformed-principal rows are meaningless for it anyway. The row that pins today's `true` goes green on origin/main — that is correct, it is the anti-tightening lock, not a vacuous test.

**D5 — The write constructors stay LOUD.** *Why:* three of `create_membership`'s seven callers DISCARD the return, so a silent denial would provision a user with no seat and report success; every caller derives its ids from a loaded row, so the crash is unreachable from client input; and mechanically, `create_membership/4`'s inline defaults mean a second clause reds `--warnings-as-errors` and forces a bodiless-head extraction on a write path.

**D6 — Semantics are preserved BY CONSTRUCTION, not by argument.** *Why:* struct clauses stay first and unmodified, the denial arm goes last, denial values follow each existing `@spec` (no return type changes), and the existing 27-test `tenancy_auth_test.exs` — which already contains all three semantics-preserved assertions verbatim at lines 228-233 — stays BYTE-UNTOUCHED as the regression net. The builder writes zero new semantics tests.

**D7 — A terminal denial arm cannot swallow a legitimate grant, structurally.** *Why:* `Membership` pins `@principal_types ~w(api_token user)` with `validate_inclusion`, so no third principal kind is representable; an unrecognised principal is a non-member, and a non-member is denied — the same answer `authorize/3`'s catch-all has always given. The mis-ordering risk the direction feared is caught at COMPILE time.

**D8 — `%CallerContext{}` is DENIED at `membership/2`, never unwrapped.** *Why:* it can carry BOTH a `user_id` and a `token_id`, so unwrapping forces the chokepoint to pick one of two identities and collapses the `principal_type` discriminator that IS the cross-kind isolation; it also drops the grants half of `authorize/3`'s decision and would let `workspace_admin?/2` start answering for a grant-bearing caller, contradicting `caps.ex`'s stated law that grants never confer admin. No caller in `api/lib` passes one to an arity-2 predicate, so denial is a behavioural no-op today.

**D9 — Do NOT unify `authorize/3` and `workspace_admin?/2`. The divergence is load-bearing.** *Why:* `authorize/3` is membership existence plus the token's GLOBAL `permissions[]`; `workspace_admin?/2` is the membership ROLE gate — which is why a global-admin token added to B as a plain `member` passes `authorize(:admin)` at B and correctly fails `workspace_admin?(B)`. That is the barkpark-23yi/fsko cross-tenant bypass fix. And share-edit tokens carry a non-nil `workspace_id` with deliberately NO membership row, so routing share-reachable surfaces through `authorize/3` would deny the entire class.

**D10 — The status-code folklore is WRONG and the correction is load-bearing for the moduledoc.** *Why:* `Ecto.Query.CastError` maps to HTTP **400**, not 500 — `deps/phoenix_ecto/lib/phoenix_ecto/plug.ex` defines `{Ecto.Query.CastError, 400}`; 500 is Plug's `Any` fallback and covers only the nil / non-binary `FunctionClauseError` class, which is unreachable at `/v1/access` because both entry guards require `is_binary`. The filed finding itself, and roughly fifteen in-repo comments, say "CastError -> 500". The honest sentence is 400 for the string class, 500 for the nil class, denial for both after the seam.

**D11 — The exception module is `Ecto.Query.CastError`, never `Ecto.CastError`.** *Why:* the latter fires ZERO times on this path across every probe run, so any `assert_raise Ecto.CastError` is vacuous — and `Repo.uuid_or_nil/1`'s own docstring names the wrong one, which is the sentence a builder reads while wiring the seam. That docstring is out of fence and filed as `task-3158c3be89815848`.

**D12 — The moduledoc says malformed ids DENY, never "never reaches the query".** *Why:* `Ecto.UUID.cast/1` accepts ANY 16-byte binary as raw UUID bytes, so a 16-byte input becomes a well-formed synthetic UUID, reaches the query, and denies by matching no row. This creates one real WIDENING that must be stated rather than smuggled: the raw 16 bytes of a live workspace id crash today and RESOLVE the real membership row after the seam. No privilege is gained — producing those bytes requires already holding the UUID.

**D13 — No `String.trim` on the seam; `Ecto.UUID.cast` and nothing else.** *Why:* a whitespace-padded UUID raises today and `uuid_or_nil` denies it; adding trim would make it start RESOLVING — a widening on an authorization path disguised as a convenience. There is an in-repo precedent for trimming on a SEARCH path; it must not be copied here.

**D14 — Uppercase-hex ids are a proven no-op; normalisation cannot deny a legitimate admin.** *Why:* run-proven against a real membership row, the canonical id, the uppercase id, the normalised id and an uppercase PRINCIPAL id all resolve the SAME row today; `Ecto.UUID.dump/1` is case-insensitive and the planner's `:binary_id` cast is a pass-through, so the set of ids that work today is exactly the set `uuid_or_nil` preserves. Preservation is by construction, not by table enumeration.

**D15 — The public-surface pin is on `{name, arity}` TUPLES, not names.** *Why:* `create_membership` is overloaded at arities 2, 3 and 4 (inline defaults on a 4-arity head), so a name-only pin — the shape of the two existing reflective precedents in this repo — collapses 11 tuples to 9 and would silently accept `create_membership/5` or an arity change on `workspace_admin?/2`. The pin must be proven able to fail with a decoy predicate.

**D16 — Every matrix row reds INDIVIDUALLY on origin/main, never as an aggregate, and the control rows must stay GREEN in both runs.** *Why:* a matrix where every row reds is not a totality proof, it is a blanket deny — the valid-UUID-unknown-workspace row and the built-in `role_permits?` row are what distinguish the two.

**D17 — The green set is FOUR test files, not the three the wish names.** *Why:* `share_controller_test.exs` serves the same `/v1/shares/tokens` routes (there is no `share_token_controller.ex`) and carries its own older malformed-id assertion — "a malformed (non-UUID) token id is a clean 404, not an Ecto CastError 500" — so proving only the two named files proves two thirds of the surface.

**D18 — The venue for the ruling is the `Tenancy.Auth` moduledoc, not `docs/contracts/tenancy.md`.** *Why:* the contract card is 8298 bytes against an 8300-byte CI cap and the doc contract forbids raising a cap; the moduledoc is in-fence and unbudgeted. The resulting gap in the card is filed as `arpss-w9-bl-tenancy-contract-doc-cannot-absorb-the-totality-fact`.

**D19 — Both builders run `opus`, not `fable`, and the depth is bought with specification instead.** *Why:* Fable is capped until Aug 21 by standing instruction. The seam slice is genuinely hard — asymmetric clause shapes, three compile traps, a doc-anchors trap and a tightening trap — so the brief carries the complete run-proven ruling set, including a working prototype's exact shape, rather than asking a builder to re-derive design judgment that this phase already did.

**D20 — Slice B is round 2, not folded into slice A.** *Why:* its assertions are false on main until the seam merges, so a round-1 builder off origin/main would produce a BLOCKED report; and keeping the security diff minimal is the whole point on a high-flip chokepoint. The cost — the 400-to-403 contract change ships unpinned for one merge — is paid by requiring slice A to STATE the change in a durable venue the merge carries and to name the round-2 task.

**D21 — `task-46e7d44068e7185e` is NOT answered by this wave.** *Why:* this wave changes only the nil ARGUMENT position; that ruling is about a nil `workspace_id` COLUMN on a token row. A reviewer skimming "nil workspace_id now denies" could wrongly believe it closed, so the moduledoc says so explicitly.
