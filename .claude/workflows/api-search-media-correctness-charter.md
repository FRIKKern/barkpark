## Decisions

- **D1 — S3 download cap is built with Req's `into:` streaming collector, NOT `max_response_size`.** Why: Req 0.6.3 (mix.lock) has NO `max_response_size` option (verified: zero occurrences in `deps/req`). The cap is an `into: fn {:data,chunk},{req,resp} -> ...` that accumulates `byte_size` and halts past the cap; cap value `100_000_000` ties exactly to the upload ceiling at `endpoint.ex:155`/`media_controller.ex:316`.
- **D2 (S3 crown-of-slice-1) — Overflow converts to an EXPLICIT error, never a silent truncated write.** Why: a naive `{:halt,...}` aborts mid-stream but Req still returns `{:ok, %Req.Response{}}` with the PARTIAL body, and `download/2`'s with-clause matches `status: 200` and would `File.write` a TRUNCATED blob and cache it. The builder stashes an overflow flag in `resp.private` (or returns `{:error, :too_large}`) so it falls into the existing `other ->` clause → `{:error, :storage_unavailable}`. The mutation test asserts the REFUSAL, not a Req-raised exception.
- **D3 — S3 mutation proof is via the Req.Test plug seam; the honesty limit is stated, not overclaimed.** Why: `req_options()` (s3.ex:355) threads `plug: {Req.Test, __MODULE__}`, and `run_plug` (req/steps.ex:1131-1138) HONORS `into: fun`, delivering the whole stub body as one `{:data}` chunk — so the over-cap REFUSAL is behaviorally testable offline and reds when the option is removed. It does NOT exercise a true mid-stream memory abort (the plug pre-buffers); the test proves refusal, and the fail-safe-against-a-real-socket property is a structural claim.
- **D4 — Rendition delete-vs-generate race is BUILT (a post-generate parent recheck), not filed.** Why: verification RAN the guard — after a successful render, `generate/6` re-queries `Media.get_file(file.id)`; row gone → `File.rm_rf` the just-written orphan and return `{:error, :parent_deleted}`. Race-sound by the delete orchestration: `Media.delete_file` commits `Repo.delete` BEFORE the deferred rendition `rm_rf`, so any write landing after `rm_rf` has its recheck see the row gone (reap), and any write the recheck keeps is caught by the later `rm_rf`. No interleaving leaves a surviving orphan; the guard introduces no new leak. Reachability is S3-backend-scoped.
- **D5 — Slice 2 converts `renditions_test.exs` from `ExUnit.Case` to `DataCase` and persists fixtures.** Why: the existing fixtures are non-persisted `%MediaFile{}` structs with no DB sandbox, so the in-fence `Media.get_file` recheck raises "cannot find ownership process" and reaps every legit fixture (3/6 fail). Verified remedy: `use Barkpark.DataCase` + `MediaFile.changeset |> Repo.insert` (id is autogenerated, use the returned struct's id) → 6/6 green. Pin the delete-orchestration ordering dependency (commit-before-rm_rf) in a code comment — a future refactor moving `delete_for_file` before the row commit breaks soundness.
- **D6 (CROWN) — Stuck-processing IS a real build: a bounded Oban-cron reconciliation sweeper.** Why: the design question was RESOLVED against origin/main — `media_processing_controller.callback` does NOT heal internal image uploads (it is an inbound external POST matching `%{"dataset","id"}`, never calls `Processing.process`, and `normalize_status(_)` even defaults unknown back to `"processing"`); internal images post-process inline via `after_media_upload` with no external processor in the loop. So a crash between the 3 non-transactional upserts strands `bp_processing_status='processing'` forever. The sweeper is modeled on `Webhooks.StuckDeliverySweeper`: `use Oban.Worker, queue: :default`; pure `sweep/1` returning `%{swept,skipped}`; oldest-first, batch-limited JSONB candidate SELECT (`type == "mediaAsset"` AND `content->>'bp_processing_status' = "processing"` AND `updated_at < cutoff`); per-row try/rescue; re-drives idempotent `Processing.process`.
- **D7 (crown termination) — The sweeper owns its OWN attempt counter and gives up to terminal `"failed"` after N re-drives.** Why: the actual stranding scenario is a RAISE (corrupt image), which never reaches `process()`'s graceful `{:error} -> "failed"` write — so a deterministic failure would loop forever. No attempt counter exists anywhere in the media domain; the builder introduces `content["bp_processing_attempts"]`, bumped by the sweeper, and writes terminal `"failed"` after N. Termination is PROVEN: the candidate SELECT excludes `"failed"`/`"ready"` by construction, so the give-up write self-removes the row (mutation-verified: a give-up that writes `"processing"` instead reds the termination test). Serialize per-row (Oban uniqueness) so overlapping ticks can't clobber a just-written terminal back to `processing`. DO NOT wrap a DB transaction over the remote-fetch/probe/transcode IO — the audit already ruled that the wrong fix.
- **D8 — Cron registration is Path B: `Barkpark.Plugins.Media.oban_crontab/0`, not `config.exs`.** Why: `collect_oban_crontab` folds a plugin's `oban_crontab/0` into the live crontab at boot via a `function_exported?` guard (verified: `application.ex:41` → `boot_collectors.ex:214`); Media defines none today; the worker binds the existing `:default` queue (a plugin can add CRONTAB but NOT queues). `plugins/media.ex` is the one file outside the literal "media + one worker" fence — media-owned and low-collision, versus shared/collision-prone `config.exs`. Collision window CLEAN at decide time (no open PR touches `plugins/media.ex` or `config.exs`).
- **D9 — Media `media.processed` double-fire on sweep recovery is ACCEPTED as at-least-once and documented; the `event_id` dedup is FILED, not built.** Why: media deliveries carry no `event_id`, so the `UNIQUE(endpoint_id,event_id)` dedup does not cover them — every sweep re-drive reaching `ready` re-fires `media.processed`. But the candidate SELECT excludes `ready`/`failed`, bounding re-fires to at most one legitimate recovery event; webhooks are at-least-once by nature. Suppression would require threading a silent flag through `Processing.process` (widens the fence into `processing.ex`) for marginal benefit. Root cause (media rows lack `event_id`) is a webhooks-side concern out of this fence — filed as `asm-bl-media-delivery-event-id-dedup`.
- **D10 — All three slices are round 1, file-disjoint, `opus@medium`.** Why: the fence partitions cleanly (`s3.ex` | `renditions.ex` | new sweeper + `plugins/media.ex`), no slice imports another's new code, so all build this run in parallel. Fable is capped until Aug 21 (the wish sets Opus) and none of these is a visually-designed surface; the crown is hard but well-specified by a copyable precedent, so a complete opus brief is the right call.

- `asm-bl-media-delivery-event-id-dedup` — media deliveries carry no `event_id`, so `media.processed` is not deduped; a sweep recovery re-fires it. Give media deliveries an `event_id` and extend the dedup constraint (webhooks-side; out of this media fence).
