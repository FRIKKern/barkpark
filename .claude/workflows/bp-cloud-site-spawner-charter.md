# Barkpark Cloud — Site Spawner Epic Charter

Epic task: `bp-cloud-site-spawner-epic` · Wave Paper (W1): `site-spawner-wave-2026-07-13` · User-facing companion: `/papers/choosing-your-site-framework`

This file is the epic's memory. Every wave reads it before planning and appends to the Wave log after. Decisions are numbered (D#) and never silently reversed — a later wave that changes one appends a superseding D# with the reason.

## Vision

One verb from content to a live URL, on the same box as the content. A user runs `bp cloud site create my-blog --framework astro --kind static --dataset ws/proj/production`, then `bp cloud site deploy my-blog`, and a dataset-bound Astro site builds next to Phoenix, fetches content over the internal link, and goes live through a health-gated, zero-downtime, instantly-rollbackable deploy engine. Astro ships first; Next.js / TanStack Start / Hugo / others ride the same **Framework-adapter × Runtime-target** engine on a clear roadmap. The deploy process is the product: reproducible + isolated builds, an atomic switch, a broken build that dies at HEALTH and never reaches a visitor, sub-second rollback, and (later) publish-to-live auto-updates. Quality bar: Kinsta/Vercel — the verbs, streamed stage status, and failure messages feel first-class.

Architecture: **Site Engine = Framework-adapter × Runtime-target matrix.** Wave 1 ships exactly ONE cell — Astro adapter × static symlink-swap target — which keeps the exec-isolation crux out of scope (tenant code runs only at build time). Deploy is ONE state machine: **PLAN → BUILD → STAGE → HEALTH → SWITCH → RETIRE**.

## Decisions

- **D1 — EXTEND, don't fork.** A content-bound static Astro site is a new `kind` cell in the existing `Registry.Site` × `Registry.Deployment` substrate, not a new subsystem. *Why:* that subsystem is sound and tested (claim-fencing, console/detail narration, per-site block pattern, `bp sites` CLI) but has **zero live rows in prod ever** — a clean, low-risk extension target; a second silent "site" concept is the failure mode.
- **D2 — Exact new columns.** `sites`: `kind` (container|static, default container — THE discriminator), `bootstrap_workspace`/`bootstrap_project`/`bootstrap_dataset` (content binding, mirroring the Barkpark row's own bootstrap triple), `read_token_encrypted` (Vault-encrypted, like `env_encrypted`). `deployments`: `build_id` (= hash(code_rev+content_rev+config)), `content_rev` (dataset revision read at build), nullable `stage` (telemetry). Unique index `(site_id, build_id)`. *Why:* `sites.current_deployment_id` ALREADY is the live pointer — add NO releases column; `build_id` both names `releases/<build_id>/` and enforces the idempotent PLAN no-op via the unique index.
- **D3 — Do NOT widen the status enum to 6.** Keep `queued→building→pushing→live(+failed/cancelled)`. The six visible stages render through the existing `console` (append-only) + `detail` (latest-wins caption) + the nullable `stage` telemetry column. *Why:* widening forces migrating `@transitions`, every CAS writer, and the stale-deployment reaper — high blast radius for cosmetic granularity.
- **D4 — Finish line = PATH-under-existing-FQDN.** Wave 1 serves at `https://<instance>.barkpark.cloud/sites/<slug>/`, via a marker-guarded Caddy `handle_path` block injected into the live FQDN block (mirroring instance-deploy.sh's `arm_caddy_mcp_route`). Astro `base` supports the sub-path. *Why:* proven live: `dig` confirms NO `*.barkpark.cloud` wildcard and BOTH live Caddyfiles are static single-FQDN with **zero `on_demand_tls`** — the wildcard/on-demand path has NEVER run on a live box, so it can't be a wave-1 guarantee. Subdomain URLs graduate later (see roadmap).
- **D5 — Static rollback = symlink repoint, kind-branched.** `bp cloud site rollback` re-points `current` to the previous release dir in sub-second, with NO rebuild. It does NOT reuse `Deployment.promotion_attrs` (which hard-codes rollback = promote-by-NEW-deployment, "never a `current_deployment_id` pointer flip" — seconds-to-minutes). *Why:* instant rollback is a wave-1 finish-line promise; the immutable `releases/<build_id>/` layout makes the flip safe by construction.
- **D6 — Content-token hardening is MANDATORY.** Mount `BarkparkWeb.Plugs.PublicRead` on the read pipeline(s) so a `public-read` token is clamped to published perspective + public-visibility schemas; BUILD mints a `public-read` token and fetches over the SCOPED route (`/w/:ws/p/:proj/...`) for tenant-membership isolation. *Why:* the plug is written + unit-tested but **mounted nowhere** (dead) — live-proven on guerrilla, a `public-read` token today reads private-schema + `?perspective=drafts` content identical to admin, and the scoped route alone is necessary-but-not-sufficient (membership decides WHICH workspace, never published-vs-draft within it).
- **D7 — Same-box BUILD, serialized + capped + env-scrubbed.** Node 26.5.0 / npm 11.17.0 is ALREADY on guerrilla (asdf, added 2026-07-13 07:51 UTC) — the "no Node toolchain" claim is stale. BUILD runs on-box, serialized (`flock`, queue depth 1) and resource-capped (`systemd-run --scope -p MemoryMax -p CPUQuota`), from a **scrubbed env** (only the injected `BARKPARK_*` build vars, nothing inherited). *Why:* the off-box builder is unshipped AND wrong-shaped (nixpacks/docker, `file://` only, zero content-fetch/token plumbing); a same-box Astro build is live-proven (38s install / 1.65s build / swap unmoved). Ambient `BARKPARK_*` silently shadows the per-site token via Vite's `process.env` precedence — hence the scrub.
- **D8 — RETIRE keeps ONLY `dist/`, N=5.** STAGE copies just `dist/` (12–16K) into `releases/<build_id>/`; `node_modules` (137–148M) stays in the ephemeral build sandbox. *Why:* node_modules is ~3 orders of magnitude larger than the artifact; N-deep `dist/` retention is trivially cheap against 22G free.
- **D9 — Static Caddy serving is NET-NEW renderer code.** The strategy's "static file_server block is an existing seam" claim is REFUTED — `grep file_server` = 0 repo-wide; `caddyfile.Render()` only ever emits `reverse_proxy 127.0.0.1:<port>`. The Go renderer gains a static `Kind`/`Root` branch (subdomain-ready foundation), but wave-1 LIVE serving uses the bash path-handle (D4). *Why:* the per-site-block PATTERN is reusable; the directive is not.
- **D10 — CLI surface = `bp cloud site <create|build|deploy|rollback|open|status>`.** A new `case "site"` in `runCloud`, backed by extended `cloudclient` Site/Deployment methods + extended `/v1/sites` routes. `bp cloud deploy` / `bp cloud rollback` stay INSTANCE-level (untouched); the existing top-level `bp sites` / `bp deploy` stay the container surface. *Why:* honor the product voice while keeping the two deploy/rollback concepts unblurred — the code already documents them as deliberately distinct; a unified alias is backlog.
- **D11 — Deploy engine = a NEW `deploy/site-deploy.sh` state machine.** Mirror instance-deploy.sh's proven skeleton (flock serialize, typed exit codes, backup+validate+reload-or-revert for any Caddy mutation, fail-closed reset-on-failure) — do NOT parameterize instance-deploy.sh itself (Phoenix-specific: mix/ecto, fixed port-pair slots, `/api/schemas` gate, git-reset rollback). HEALTH = a throwaway static file server on a loopback ephemeral port over `releases/<build_id>/`, asserting 200 AND the `bp-build-id`/`bp-content-rev` marker baked into `index.html` (content-truth, not just reachability — "distrust vacuous green"). SWITCH = atomic `current` symlink `rename(2)`, no Caddy reload in the flip. *Why:* static builds have no process to boot/restart; the immutable `releases/<build_id>/` layout sidesteps the shared-checkout rollback bug class by construction.
- **D12 — Deferred (seeded as backlog, NOT built this wave):** node-slot SSR runtime-target (+ per-site port allocator + generic systemd template unit); content-webhook auto-rebuild/debounce (reuse the indx/edge_projector Oban debounce lifecycle-hook pattern, NOT webhook-to-self); every non-Astro adapter (Hugo next); subdomain-URL graduation (wildcard-per-instance + first live `on_demand_tls` run); per-workspace run-secrets scoping; `bp sites` ↔ `bp cloud site` unification; broad-exposure build sandbox with true exec-isolation. *Why:* wave-1 static builds are build-time-only (no runtime tenant code) — no isolation crux this wave; note it for the SSR wave.

> **D13–D32 landed in Waves 2–3** and are recorded in the wave Papers `cloud-site-spawner-wave-2-2026-07-14` and `cloud-site-spawner-wave-3-2026-07-14` (the spine: BPSTAGE protocol, value-asserting HEALTH, `/v1/admin/site-deploy` relay seam, kind-scoped reaper, CLI honesty, Caddy TLSMode, the six false-green kills). They are NOT re-transcribed here to avoid bloat; grep those Papers for the D#. Wave 3 closed **B+** with a blunt verdict: THE WISH IS NOT MET — no live spawn had ever served a page. Wave 4 (below) closes that.

### Wave 4 — Source provisioning to a live URL (D33–D41)

- **D33 — PROVISION lives BOX-side in the on-box executor, not `cloud/`.** Materialize `templates/astro-starter` → `/opt/barkpark/sites/<slug>/src` inline in `DeployRunner.start_run/2` (api/lib/barkpark/sites/), before `open_port(req)`. Use the STAGE partial-rename idiom (`src.partial` → `mv src`), marker-guarded idempotency (write `.bp-provisioned` only after a successful rename; re-provision overwrites cleanly, never appends), fail-closed (a materialization error returns `{:error, :provision_failed}` — never a half-materialized `src/`). Provision touches ONLY `src/`, never `releases/`/`current`/`.previous`. *Why:* PROVEN — `start_run/2:258` is the SOLE path to the site `Port.open`; `box_relay.ex`/`cloud/…/deploy.ex` are HTTP relays that never run on the box. Same-process, same admin trust boundary, `File.cp_r!` of the 188K/10-file template measured **12 ms**. Supersedes the wish's imprecise "cloud/deploy.ex / box_relay.ex" home.
- **D34 — PROVISION is a SILENT pre-BUILD step, NOT a visible 7th stage.** Zero changes to `@stages`/`@stage_names`/the six-name contract. Provision succeeds before BUILD's Port opens, or the deploy fails before it starts. *Why:* a 7th visible stage is a 13-file blast radius (two hardcoded BPSTAGE parse regexes at deploy.ex:723/742 that do NOT read `@stages`, ~10 test fixtures, charter D11 governance). A pre-Port step is one file + one new module. site-deploy.sh keeps its deliberate no-scaffold contract — its `exit 10`/`exit 11` stay as a belt-and-suspenders guard for a provision that somehow didn't run.
- **D35 — DOC_TYPE is PLUMBED END-TO-END this wave** (reversing the survey's "default-and-defer" lean). *Why:* the crux was settled by LIVE proof — guerrilla `production/post` → **404, zero post docs / no post schema**; `production/paper` → **200, count 100**; a real `npm run build` with `BARKPARK_DOC_TYPE=post` **HARD-FAILS (exit 1**, uncaught `BarkparkNotFoundError`), and with `paper` builds green + bakes real non-empty `bp-doc-id`/`bp-doc-title`. The template default `'post'` is therefore unsafe on guerrilla, and passing `doc_type` via an env prefix is INERT (the CLI swallows it, BUILD_ALLOW drops it, DeployRequest 400-rejects it). A green live proof REQUIRES `doc_type=paper` to actually reach the box. Plumb 7 sites: `sites.doc_type` column (default `"post"`) + migration; `deploy_payload` `BARKPARK_DOC_TYPE`; `DeployRequest.@allowed_env_keys`; `site-deploy.sh` `BUILD_ALLOW`; router `put_site_content_binding` + create attrs; `cloudclient.SpawnSiteCreate.DocType`; CLI `--doc-type`. Default stays `"post"` (canonical); the proof passes `--doc-type paper` explicitly. `BARKPARK_DOC_ID` stays DEFERRED — `fetchFlagshipDoc` falls back to newest-of-type, pinning is not needed for the proof.
- **D36 — FORCE NONCE.** `enqueue/2` + `build_id/3` gain a `force` param; when `force`, fold a nonce (`System.system_time()`) into the `config` map so `build_id` changes on identical content and a genuinely new `releases/<build_id>/` is minted. Default path stays byte-identical and idempotent — the existing "repeat build of same code+content+config is a no-op" test (sites_deploy_test.exs:84) is the tripwire and MUST still pass. Router `deploy_static_site` reads `conn.body_params["force"]`; CLI adds `--force`. *Why:* `{force:true}` is entirely unbuilt — an unchanged re-deploy returns the cached duplicate and can't re-run.
- **D37 — nil/undecryptable read token FAILS CLOSED.** `drive/3` reveals the token before `BoxRelay.start_deploy`; a non-`{:ok, binary}` routes to `fail(ctx, "site read token missing or unreadable")` — the deployment settles `failed` with an honest reason, the box is never touched, never a raise. *Why:* deploy.ex:239-243 today degrades a missing token to `nil` `BARKPARK_TOKEN` → build fetches unauthenticated → empty content → empty `bp-doc-id` → judge_live red; contradicts the fail-closed mandate.
- **D38 — `BARKPARK_SITE_DEPLOY_APPLY=1` is PERSISTED in the slot-env generation source.** instance-deploy.sh:548-549 truncate-regenerates `.slots/{blue,green}.env` every deploy with a 2-key printf (`BARKPARK_PORT_OVERRIDE`, `MIX_BUILD_ROOT`) that silently drops the seam-enable flag; the generator preserves the flag across a redeploy, with a new `instance-deploy_test.sh` case that seeds it pre-deploy and asserts survival. *Why:* PROVEN — a redeploy drops the flag → the site-deploy admin route reverts to 503 → the whole finish line re-breaks. The flag is read at BEAM boot from that EnvironmentFile.
- **D39 — CLI STREAMS running stages** (Kinsta/Vercel bar). `streamSiteDeploy`'s `render()` filter is relaxed to print the running/started transition, keyed by **(name+status)** NOT name-only — the name-only `printed[]` map would otherwise swallow the terminal done-line once a "running" line is printed. *Why:* the box already emits `started` (arrives as status `running`); today the CLI is silent for the whole ~38s BUILD.
- **D40 — DEFERRED, do NOT fold this wave:** teardown/DELETE verb (touches router.ex + site-deploy.sh + BoxRelay + registry — a cross-surface slice that collides with the deploy-inputs slice and blows the wave's parallel file-disjointness; the live proof uses a uniquely-slugged site + the existing printed cleanup note instead); the `@barkpark/core` `findOne()`-throws-on-empty-result robustness fix + `BARKPARK_DOC_ID` plumb (a real fragility — any future site whose doc_type has zero published docs BUILD-crashes instead of building honestly empty — but the proof is green with `paper`'s 100 docs); build-allow-ambient (DeployRunner's set-or-remove `child_env` already closes the real shadow hole — site-deploy.sh's header is a doc-only overclaim); content-rev-truth (`{force:true}` sidesteps it for the proof); token-revoke; cli-site-create-dataset-flag-eaten; sobelow-baseline-reconcile. *Why:* fold ONLY the critical path to a green 6-stage live proof + sub-second rollback.
- **D41 — Live proof binds `paper`.** `deploy/site-spawner-live-proof.sh` creates with `--doc-type paper` (D35 chain carries it to the box), asserts a `≥1 published paper` precondition before the `bp-doc-id` non-empty check, uses `--force` at step 4 (D36) so rollback has two distinct builds, and walks all six stages green to a served URL + sub-second rollback. *Why:* the empirical content reality (D35) plus the force nonce (D36) are exactly what let judge_live and judge_rollback go green.

### Wave 5 — Publish-to-live auto-update (D42–D50)

Closes the LAST original "perfect deploy" gap: edit in Studio → hit Publish → the bound co-located site re-deploys itself, no manual `bp cloud site deploy`. PLAN-light, BUILD-heavy — the 6-stage machine, force-nonce (D36), fail-closed HEALTH, the box Webhooks.Dispatcher and Oban-on-CP are ALL built and proven. This wave WIRES an existing trigger to an existing event bus + adds ONE provenance field + a live proof. The crux was settled by architecture (5 surveyors unanimous) and RUN-proven by 7 verifiers on origin/main.

- **D42 — CP OWNS binding + trigger; the box only NOTIFIES, reusing the existing Webhooks.Dispatcher.** The site→dataset binding (`sites.bootstrap_workspace/project/dataset`) lives EXCLUSIVELY on the CP (`cloud/…/registry/site.ex`); `api/` has zero schema/code for it (grep of `api/lib` = nothing). PubSub is in-node only. So at site-create the CP registers ONE dataset-scoped webhook row ON the box (via the existing admin-token relay `Registry.relay_admin/4`, the `wire_site_url` prior art) pointed at a NEW CP inbound receiver; the box's publish path (`Content.tap_broadcast` → `Webhooks.Dispatcher.dispatch_async`, txn-deferred, HMAC-signed, retrying, dedup on event_id) fires HMAC HTTP off that same publish with ZERO new box-side code. *Why:* the only existing off-box transport off a publish is the Dispatcher; PubSub can't cross to the CP. Resolves D12's "NOT webhook-to-self" — box (guerrilla) and CP (barkpark.cloud) are distinct PUBLIC hosts, and `SafeOutbound` blocks only private/loopback/metadata, so it is a genuine cross-host public call, not self.
- **D43 — Trigger set = {publish, unpublish, delete} — the 3 lifecycle actions that touch the PUBLISHED row.** Register the box webhook with `events:["publish","unpublish","delete"]`. create/update coerce to draft (`writer.ex` `Map.update("status",…"published"->"draft")`) and never change what a visitor sees; discardDraft touches only the draft row; patch never emits (resolves internally to "update"). *Why:* proven by a repo-wide `tap_broadcast(` sweep — 11 sites, ALL under `content/`; only `lifecycle.ex` carries publish/unpublish/delete. Rebuilding on draft saves would fire a ~10s npm build per keystroke-save for zero live-content change. delete-of-a-draft-only doc fires "delete" harmlessly (debounce + fail-closed HEALTH absorb it as a no-op) — the skip-refinement is DEFERRED.
- **D44 — ONE CP-side debounce: an Oban `unique` job keyed on `site_id`, states `[:available, :scheduled]` — DROP `:executing`.** This is a load-bearing CORRECTION to D12's "reuse indx/edge_projector verbatim." The prior-art clause includes `:executing`, which (PROVEN BY RUN, verify V1) SWALLOWS a publish that lands mid-build: while job A is `:executing` a new publish matches A (state ∈ states, still within the 30s period off `inserted_at`) → conflict → nothing inserted → A already snapshotted content at build start → the site silently serves STALE content, the EXACT failure the wish forbids (a ~10s npm build sits entirely inside the window). Dropping `:executing` makes a publish-during-build find NO conflict (A is `:executing` ∉ states) → mint exactly ONE trailing rebuild carrying the new content; a burst BEFORE build still collapses to one `:scheduled` job. `schedule_in` a short window (~5s, indx precedent). The deploy queue MUST be effectively serial per site (concurrency 1 / same-site unique) so the trailing rebuild runs AFTER the in-flight build, not concurrently. Box notify stays UNDEBOUNCED (no box+CP double-debounce). cloud/ runs Oban 2.23.0 (supervised, `maintenance` queue) — the substrate exists; the "cloud/ has no Oban" comments are stale. *Why:* both wish clauses ("10 publishes = 1 rebuild" AND "the site still updates after the current build") hold simultaneously ONLY with `:executing` dropped — proven by a passing scratch test (trailing==[] for the prior-art clause, length==1 for the fix).
- **D45 — The receiver is PER-SITE: `POST /v1/sites/webhooks/content-publish/:site_id`, mirroring `/v1/webhooks/github/:site_id`.** The receiver loads the site by `:site_id`, verifies HMAC against the site's own stored secret, then enqueues the D44 debounced auto-deploy for THAT site. *Why:* this ELIMINATES the dataset→sites resolver AND the `barkpark_id`-scoping correctness trap V5 flagged — `(workspace,project,dataset)` is NOT unique across the `sites` table (no DB constraint; two boxes sharing default slugs like `production`/`main` would cross-trigger), but `site_id` is the PK, unambiguous across boxes. The box already fans a publish out to ALL sites bound to a dataset by firing one Dispatcher delivery per registered webhook row (`active_webhooks_for`), each to its own `:site_id` endpoint — the fan-out is free, the routing is exact. Per-site is strictly the GitHub-bridge precedent, not new.
- **D46 — CP-side HMAC verifier mirrors `StripeGateway.check_signatures`, NOT the GitHub verifier.** The box signs `x-barkpark-signature: t=<unix>,v1=<hex>` = HMAC-SHA256 over material `"<timestamp>.<body>"`, ±300s tolerance, secrets LIST (rotation). `cloud/…/billing/stripe_gateway.ex` is BYTE-FOR-BYTE this scheme (same `"t.payload"` material, lower-hex, `t=,v1=` grammar, 300s window) and lives in the SAME mix app; port a ~40-line `Sites` verifier from it. The existing `verify_github_signature` is a DIFFERENT scheme (`sha256=<hex>` over raw body, NO timestamp) and would REJECT every valid delivery or open a replay hole — DO NOT copy it. cloud/ cannot call api's `Dispatcher.verify_signature/5` (separate mix apps, and it is caller-less/api-side). New route added to `@raw_body_path_prefixes` (`"/v1/sites/webhooks/content-publish/"`), unauthenticated (HMAC IS the auth), mirroring the `/v1/billing/webhook` receiver shape.
- **D47 — The webhook secret is per-site: `sites.content_webhook_secret_encrypted` (Vault-encrypted, mirroring `github_webhook_secret_encrypted`).** The CP mints the secret at registration, passes it in the box create call (`Webhook.changeset` casts `:secret` on CREATE — update drops it; create exposes it once), stores the ciphertext (`Vault.encrypt/1`, the exact `registry.ex:3774` pattern), and verifies inbound against `reveal`-decrypted plaintext. Registration fires at `create_site` for `kind==static` sites with a bootstrap_dataset when the instance is live (relay in tests is the FakeBoxRelay). *Why:* the CP must hold the secret to verify inbound; per-site storage matches the per-site receiver (D45).
- **D48 — Auto-deploy enqueues with `force=true` + `trigger="content-auto"`.** After the D44 debounce coalesces to a single fire, the receiver calls `Sites.Deploy.enqueue(site, bp, true)` with the trigger provenance. `force` folds a `System.system_time()` nonce into `build_id` so a byte-identical republish still mints a fresh `releases/<build_id>/` (belt-and-suspenders — a real publish already changes `content_rev` → a fresh build_id, but force guarantees it). `force` is safe HERE precisely because the debounce guarantees single-fire: `force` is the OPPOSITE of a dedup key (two un-coalesced forces = two real builds), so the `site_id`-keyed Oban unique (D44) is what prevents the race, not the `(site_id,build_id)` index. Fail-closed HEALTH + force-nonce then inherit FOR FREE — `settle_live` fires only on `:succeeded`, `normalize_state` "failure beats the lifecycle word," pinned by `sites_deploy_test.exs`.
- **D49 — Provenance = one `deployments.trigger` column (`manual|content-auto`, default `"manual"`).** Migration mirrors the `environment` enum (`@triggers`, `validate_inclusion`). Threads: `create_deployment` attrs → `Sites.Deploy.enqueue` → `deployment_json/1` (the SOLE base serializer — `site_deployment_json/3` and `deployment_with_site_json/1` both pipe through it, so list/get/deploy-response/agent-claim get it free). Manual deploys stamp `"manual"`; the receiver stamps `"content-auto"`. THE GO CLI IS NOT FREE (verify V2): Go's `json.Unmarshal` silently DROPS unknown keys (no `DisallowUnknownFields`), so `trigger` is invisible until threaded through `internal/cloudclient/client.go` `SiteDeployment` struct + `internal/cli/cloud_site_cmd.go` `siteDeploymentMap`/`spawnSiteStatusMap` + `streamSiteDeploy` narration — `environment`/`content_rev` are already dropped today exactly this way. The wish's "observable" bar requires the Go surface, not just the column.
- **D50 — Live proof is a NEW harness `deploy/site-spawner-autorebuild-proof.sh` (leave the proven manual `site-spawner-live-proof.sh` untouched).** It creates a content-bound site, PUBLISHES a NEW paper to the bound dataset on guerrilla, and asserts the bound site AUTO-rebuilds — a new deployment row with `trigger=content-auto` reaching a live URL whose `bp-doc-id`/`bp-content-rev` reflect the new content within a bounded time (≤60s from publish), plus a burst assertion (N rapid publishes → ONE/one-trailing rebuild). Offline `--self-check` mode drives every typed red (mirroring the existing harness); the LIVE guerrilla walk is merge-gated and run by the lead after the CP auto-deploys. *Why:* a new file keeps the wave file-disjoint and preserves the proven manual capstone; the auto-rebuild flow is a genuinely different journey (publish→observe, not create→deploy→rollback).

## Roadmap

Wave 1 (this wave) — the STATIC-Astro deploy spine, end to end:
1. **cloud-site-schema** (cloud/, large) — kind + dataset-binding + read_token on `sites`; build_id + content_rev + stage on `deployments`; unique (site_id, build_id); kind-gated framework legality; the missing `site_test.exs`. [D1, D2, D3]
2. **static-deploy-engine** (deploy/, large) — `deploy/site-deploy.sh`: 6-stage state machine, symlink-swap SWITCH, marker-asserting HEALTH, N=5 RETIRE, sub-second `--rollback`, path-handle Caddy arm, flock+systemd-run BUILD isolation, env scrub. [D4, D5, D7, D8, D11]
3. **astro-adapter** (templates/, medium) — `templates/astro-starter/`: build-time content fetch over the scoped route, `base` sub-path, `bp-build-id`/`bp-content-rev` markers. [D4, D6, D7]
4. **bp-cloud-site-cli** (internal/cli + internal/cloudclient, medium) — `bp cloud site create|build|deploy|rollback|open|status` + cloudclient methods. [D10]
5. **content-token-hardening** (api/, medium-large) — mount `PublicRead`; integration test proving a public-read token is clamped on a real routed request. [D6]
6. **caddyfile-static-kind** (internal/caddyfile + internal/runtime, medium) — Go renderer static `Kind`/`Root` branch (subdomain-ready foundation; not wired to live serving this wave). [D9]

Wave 2+ (deferred backlog, see D12) — ~~content-webhook auto-rebuild (Oban debounce)~~ **BUILT in Wave 5 (D42–D50)**; subdomain-URL graduation (wildcard-per-instance + on_demand_tls live proof); node-slot SSR runtime-target; Hugo adapter (proves the engine serves a second static framework); `bp sites`↔`bp cloud site` unification; per-workspace run-secrets scoping.
