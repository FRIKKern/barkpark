# bp Login UX Epic — Charter

Epic task: `bp-login-ux-epic` (published, guerrilla ledger). Wish: first-screen Cloud login in the wizard + Claude-Code-style copy-link browser auth for `bp login`, with email+password kept as the headless/CI fallback.

## Vision

A fresh user types `bp` and the wizard's first screen offers **Barkpark Cloud — log in and pick your barkpark** as a first-class target alongside Connect/Local/Deploy/Provision. Choosing it — or running bare `bp login` on a TTY — starts a device-link handshake: the CLI prints a boxed copyable URL + short code (`https://barkpark.cloud/activate` · code `XXXX-XXXX`), offers to open the browser, and spins while polling. The user approves in the browser riding their existing barkpark.cloud session (2FA handled by the web flow for free). The control plane mints the **exact same UserToken session** `POST /v1/auth/login` mints; the poll returns the identical `{token, team_id}` envelope; the CLI stores it exactly where `runLoginCloud` does (SaveConfig, 0600). Then the wizard doesn't dead-end: it lists the team's barkparks, fetches instance credentials, and drops into the ordinary Connect path — Cloud login IS a complete setup. `bp logout`, session list, and bulk revoke work on device-minted sessions with zero special-casing.

## Decisions

1. **RFC 8628-shaped protocol, new `device_auth_requests` table** (not a `user_tokens` context row, not `oauth_states`) — the two-secret model (`device_code` for polling + `user_code` for approving) with a pending→approved lifecycle fits neither existing store (device-flow-prior-art explorer confirmed).
2. **Session minted at POLL time, not approve time.** Approve only stamps `user_id` on the row (pending→approved, CAS). The successful poll consumes the row atomically (delete/update count==1 discipline, mirroring `OAuth.consume_state`, oauth.ex:205) and THEN calls `Accounts.create_user_session_token/2` — so no session plaintext is ever at rest, and a replayed poll fails closed.
3. **Poll success envelope is byte-identical to login**: `{token, team_id}` with `team = Accounts.primary_team(user)` (router.ex:262-264). This is what makes CLI storage reuse trivial and keeps the Go `LoginResp` struct unchanged.
4. **Session opts = the CLI's IP + User-Agent captured at device-START** (stored on the row), passed to `create_user_session_token` at mint — so GET /v1/account/sessions shows the bp machine, not the approving browser.
5. **Approve requires an authenticated browser Bearer session** (`Auth.require_user`) — this is what preserves the 2FA gate, since the mint function itself doesn't enforce 2FA (login diverts BEFORE minting; accounts.ex:1690, router.ex:259). Never let approve run unauthenticated.
6. **Approve page = SPA view at real path `/activate`** (one `get("/activate", do: send_dashboard(conn))` route next to `/new`, router.ex:225). Logged-out visitors ride the existing park-in-sessionStorage → scrub URL via history.replaceState → banner login → resume-on-first-authed-render pattern (app.js:4918-4970 invitations/instance-login precedent). Page shows code + requesting host/IP/UA and explicit Approve/Deny buttons — never auto-approves. `?code=` prefill allowed but scrubbed after read; user can always type the code.
7. **Codes**: `user_code` = 8 chars displayed `XXXX-XXXX`, CSPRNG over the unambiguous alphabet `23456789ABCDEFGHJKMNPQRSTVWXYZ` (~39 bits — enough that an authed attacker can't guess-approve within TTL under rate limits); `device_code` = 32-byte `:crypto.strong_rand_bytes |> Base.url_encode64` (accounts.ex:2010 idiom). **Both hashed at rest** with the shared SHA-256-hex scheme (`UserToken.hash_token`, user_token.ex:228); lookups are by hash of the presented value; any residual in-memory compare uses `Plug.Crypto.secure_compare` (already a dep, web/auth.ex:184).
8. **TTL 600s, poll interval 5s.** New `DeviceAuthRateLimiter` GenServer-owns-ETS sibling of `TwoFactorRateLimiter` (do NOT share its table — key shapes differ), generic `check(key)` keyed `"poll:"<device_code_hash>` (limit 20/60s → 429 `{"error":"slow_down"}`), `"start:"<peer_ip>` (10/60s), `"approve:"<user_id>` (10/60s). Registered in application.ex next to the 2FA limiter.
9. **Expiry**: enforced in-band by every query (`expires_at > now`, like oauth.ex:210); an Oban `DeviceAuthReaper` (`queue: :maintenance`, per-minute crontab entry in config.exs:189-197, copy StaleProvisionJobReaper) is hygiene only. Migration copies `create_oauth_states.exs`: binary_id pk, unique indexes on both code hashes, `expires_at` sweep index.
10. **Endpoints** (all JSON, in cloud router):
    - `POST /v1/auth/device/start` (unauthed, rate-limited by IP): req `{client_name}` → 200 `{device_code, user_code, verification_uri, verification_uri_complete, interval: 5, expires_in: 600}`. Server captures peer IP + User-Agent onto the row.
    - `POST /v1/auth/device/poll` (unauthed, rate-limited by device_code): req `{device_code}` → 200 `{status:"pending"}` | 429 `{error:"slow_down"}` | 200 `{token, team_id}` (consume+mint) | 404 `{error:"expired_or_invalid"}` (covers expired, denied, replayed).
    - `POST /v1/auth/device/inspect` (Bearer, require_user): req `{user_code}` → `{client_name, ip_address, user_agent, expires_at}` for the confirm screen.
    - `POST /v1/auth/device/approve` (Bearer): req `{user_code}` → `{ok:true}`; pending→approved CAS, stamps user_id; second approve fails.
    - `POST /v1/auth/device/deny` (Bearer): req `{user_code}` → deletes the row.
11. **CLI gating** (backward-compat is hard): device flow engages ONLY when there are zero credential inputs (no `--email`/`--user`, no `--password`/`--pass`, no `BARKPARK_PASSWORD`) AND both stdin+stdout are TTYs (`canRunWizard` both-streams isatty idiom, setup_cmd.go:285). `--device` forces the device flow. Any credential input or non-TTY → the existing password path verbatim (headless/CI untouched). `bp login --email x` still password-prompts as today.
12. **`-o json` contract unchanged**: final success envelope stays `{ok, cloud_url, team_id}` via `emitStructured`; all device-flow chrome (box, spinner, fallback line) goes to stderr (`out.errf`). Storage = set `cfg.CloudURL/CloudToken/CloudTeam` + `SaveConfig` (0600 guaranteed by SaveConfig itself, config.go:260) — identical to runLoginCloud:113-115. Poll throttle maps to `exitRateLimit=7` retry-internally, terminal failures to `exitAuth=3`.
13. **Wizard integration = Option A (thin bridge, callback hook)**: `TargetCloud = "cloud"` added to `targetChoices` (row 2, after Connect); picking it short-circuits the remaining stages and returns `SetupPlan{Target: TargetCloud}`. The setup package gets a `CloudLogin` hook on `setup.Options` (nil = target hidden/errors) that the CLI layer injects; the CLI-side implementation reuses the SAME device-login routine as `bp login` (factored into `internal/cli/login_device.go`), then `ListBarkparks` → numbered pick → `GetCredentials(id)` → feeds `{Server: creds.URL, Token: creds.AdminToken, Name: barkpark name}` into the ordinary `executeConnect`/`RememberServer` path. `SavedConfig`/`ConfigStore` stay untouched (no Cloud* fields).
14. **Fleet edge cases**: empty fleet → print launch/deploy guidance and exit 0 (user IS logged in — that's success, not a dead-end); `GetCredentials` 404 `no_admin_token` → explain and prompt the user to paste a token (falls into the same Connect path), or skip connect and finish logged-in.
15. **Persisting the AdminToken as the saved server token is accepted** — same trust level as a user pasting it into Connect today, config is 0600. Explicit posture decision, noted here so it's never re-litigated silently.
16. **Docs live at `docs/setup/cloud-login.md`** (doc-tier: human) — README/INDEX byte caps are full; no new agent card (7-card cap). Do not touch the agent-onramps docs (docs/setup/CURSOR.md etc.).

### Wave 2 decisions (2026-07-09 — "sign-in IS setup")

17. **Auto-register guard is `activeSavedServer().ok` — NEVER `FirstRun()`.** A cloud login SaveConfig creates the config file, so FirstRun() flips false the moment a token is stored (config.go:190-202) and cannot distinguish "just logged in, no content server" from "configured". activeSavedServer() (setup_cmd.go:76-91) returns ok=false for both virgin and logged-in-never-connected — both safe to auto-connect (nothing to steal). Branches: **ok=false → auto-connect**; **ok=true + same server → reconnect** (refresh via the same connect path, announce "reconnected to <name>"); **ok=true + different server → report, don't steal**: "already connected to X; your cloud fleet has Y — `bp setup` to switch", finish logged-in, exit 0. Comparison MUST normalize BOTH sides with `normalizeServerURL` (config.go:140) after canonicalizing the fleet target to a scheme+host URL — `fleetTarget` can return a bare host (setup_cloud_login.go:212) that would falsely read as a different server. On the reconnect branch never trust `entry.Token` (activeSavedServer can return ok=true with an EMPTY token, setup_cmd.go:90); use the fresh GetCredentials admin token.
18. **The steal-guard lives in the LOGIN TAIL only.** The wizard's Cloud target is explicit user-initiated setup — picking it IS consent to repoint (same trust as Connect today). `cloudFleetPick` stays guard-free; RememberServer always repoints (config.go:319-320, no save-without-repoint path), so the guard must sit BEFORE the connect delegation.
19. **One fleet routine, two callers — via an n==1 fast path INSIDE `cloudFleetPick`.** Single-barkpark fleet skips the numbered prompt: GetCredentials on the one entry, same creds→target→CloudLoginResult tail, same `no_admin_token` → `cloudNoAdminToken` manual-paste fallback. Multi keeps the pick. The wizard hook (cloudLoginHook) inherits the fast path for free. **The empty-URL/still-provisioning branch (setup_cloud_login.go:159-161) converts from ERROR to a LoggedInOnly non-dead-end** ("you're logged in; <name> is still provisioning — re-run `bp setup` when it's ready") on BOTH the fast path and the pick path — today it hard-fails, violating decision 14.
20. **The login tail convergence point must be BUILT — it does not exist.** Device and password paths never converge after token save (device returns exitOK at cloud12_cmd.go:97; save+surface live inside runDeviceLoginFlow). New shared `finishLoginConnect(out, cfg)` called from runLoginCloud's device tail AND password tail: gate `out.isTTY && !out.machineOut()` (both conjuncts load-bearing — machineOut covers `-o json` on a tty, isTTY covers `-o table` on a non-tty; do NOT rely on the json early-returns), interactive multi-pick additionally gated on both-streams TTY (deviceTTYCheck idiom). It resolves the fleet via cloudFleetPick, applies decision 17, and delegates to `setup.Execute(SetupPlan{Target: TargetConnect,…})` with `configStoreAdapter{}` — byte-equivalent to a wizard pick, no hand-rolled connect. **The dead-end hint "run 'bp barkparks' to see your fleet" is REMOVED from `emitDeviceLoginSuccess` (login_device.go:178) and the password tail (cloud12_cmd.go:147)** — it currently also mis-fires mid-wizard; runLoginCloud owns the post-login narration. Fleet-resolution failure AFTER a successful login = stderr warning + **exit 0** (logged-in is a complete outcome, decision 14; never exitAuth).
21. **Headless contract frozen.** `-o json`/`-o yaml` and non-TTY get ZERO new behavior: envelope `{ok, cloud_url, team_id}` byte-identical, no prompts, no auto-connect. No `--register` opt-in flag this wave (backlog).
22. **Announcement = one-line prefix + the existing premium summary.** `finishLoginConnect` prints `Connected to <name> — <url>` (the acceptance-criterion line) and lets executeConnect's existing summary (connect.go:118-132: tier, scope, next steps) stand — reuse gives more than the wish asked; do not fight or duplicate it.
23. **Take me further = signal-to-main sentinel (option A), plus the empty-active-server hint fix.** The desk lives in package main, unreachable from cli — after a successful auto-connect on a TTY, standalone login offers "Press Enter to open the desk"; on Enter, runLoginCloud returns an exported sentinel exit code that cmd/barkpark/main.go interprets as "launch runTUI" instead of exiting. Terminal-safe by the wizard→desk precedent (cooked-mode line I/O only, Bubble Tea opens the tty fresh). Re-exec rejected (argv[0] fragility). **Separately, main.go's fall-through hole gets fixed**: configured==true is just !FirstRun(), so LoggedInOnly outcomes (empty fleet, no_admin_token skip, blank-skip) with c.Server=="" currently reach the desk resolution and print the misleading "Is the Phoenix API running?" (main.go:57) — empty active server must route to setup guidance instead. The stale-config seam suspected in W1 is DISPROVEN: config is disk-only, re-read fresh on every LoadConfig; SaveConfig is atomic temp+rename before RunFirstTimeSetup returns.
24. **`/activate` canonicalizes to the dashboard host — subdomain-conditional, zero new config.** `activate_url` (router.ex:8220-8226) prefers `Application.get_env(:barkpark_cloud, :dashboard_url)` (config.exs:245, DASHBOARD_URL-overridable) **only when `conn.host` equals or is a subdomain of the dashboard host** (api.barkpark.cloud → https://barkpark.cloud/activate); otherwise the existing request-host construction stands, so local dev (`--url http://localhost:4100`) keeps boxing localhost and the e2e loop stays whole. Naive unconditional reuse would break local device login (:dashboard_url is barkpark.cloud in ALL envs). Redirects rejected — the box is a copied STRING; both hosts already serve /activate 200 against one shared DB, so cross-host approve is safe. **Docs consequence inverted from the wish**: docs/setup/cloud-login.md already promises barkpark.cloud/activate (lines 19/28/108/111) — this change makes the docs true; the api.barkpark.cloud mentions at lines 43/88 describe the API base and stay.
