# Email Fleet Components — Epic Charter

Epic ledger: `gui-premium` (published) → wave task `gp-w4-email-components` (adopted, published, GH #1667) → three slice children `gp-w4a/b/c` (this wave).

## Vision

The mailed paper is a flagship brand surface. Open `/papers/portabledoc-showcase/email` in Outlook and §4/§6/§8 read as REAL components — task rows with colored status glyphs, a legible mini task-board, cards with tone accents, a reader-faithful terminal panel, side-by-side columns — not unstyled text runs. All 14 fleet block types (tasks/task-list, task-detail, task-board, roadmap, notes, note, cards, card, pipeline, stage, terminal, columns, status-legend) get `:email` inline-styled variants exactly like DataViz got in #1660 and prose got in #1830: `<table cellspacing=0 cellpadding=0>` scaffolding, every color theme-resolved through generated accessors, article emitters byte-untouched.

## Decisions

- **D1 — Clone the DataViz THREE-clause split per fleet type; do NOT thread theme through the recursion seam.** Per type: keep the `:article` `/2` clause → `Components.*_html` classed (byte-untouched, gate-locked); add a `_style` `/2` clause → `*_email_html(b)` (evergreen default); add a `/3` `when style != :article` clause → `*_email_html(b, theme)`. Nested fleet (terminal⊃task-list, section⊃cards) thereby gets its EMAIL variant at evergreen automatically — same accepted tradeoff as DataViz (compose.ex:44–49). *Why:* exploration proved the `/3` fallthrough (compose.ex:79) already drops theme before recursion; threading it fans out to ~6 compose helpers + 7 Components fns for zero acceptance-surface benefit — the email envelope renders evergreen and "dark" in email is the mail client's transform of the same bytes, not a second render.
- **D2 — Status/tone colors come from `StatusVocab.tones()` (status-manifest), NOT `TokensGen.tone_*`.** Role→tone map is static logic in the email modules: done→`:ok`, in_progress→`:info`, blocked→`:warn`, danger-tone cards→`:danger`; ready→`email_skin.text`, open/cancel→`email_skin.muted`. Skin (ink/muted/accent/ground/border/paper) via `Palettes.email_skin(theme)` per the DataViz `email_skin/1` template (data_viz.ex:371). *Why:* tokens.json itself notes `color.status` ("ok" green #137236) is DELIBERATELY distinct from lifecycle done teal #0d9488; the reader's `--st-*` come from status-manifest.json, which `StatusVocab.tones()` already exposes in Elixir — using TokensGen.tone_* would visibly diverge from the reader and fail visual acceptance. No generated-file edit needed (Path B), so no prerequisite slice.
- **D3 — Three sibling emitter modules, one per slice, each with its own private skin/tone helpers.** `render/fleet_email.ex` (task family), `render/cards_email.ex` (cards/notes/pipeline family), `render/panels_email.ex` (terminal/columns/status-legend). *Why:* three parallel builders must not share a new file; the ~15-line helper duplication mirrors DataViz's private `email_skin/1` and the reviewer can dedupe post-wave.
- **D4 — Table-first layout doctrine; terminal is LIGHT.** Rows = glyph-cell + text-cell + meta-cell tables; grids (task-board, cards, columns, pipeline) = fixed multi-cell tables (Outlook's only reliable grid); roadmap bars = nested spacer-table percentages. The reader's terminal is light-chromed (ink-tint bar, paper-surface.css:661), so the email terminal matches the reader — the direction's "dark panel" is overruled by reader parity. Terminal traffic dots hard-code `#ef4444/#f59e0b/#22c55e` with a comment: the reader hard-codes the same untokenized hexes — the one documented literal-hex exception.
- **D5 — Honest degradations (decided up front, not improvised):** roadmap drops the absolute `today` marker (the only genuinely undrawable element); momentum shimmer → static accent fill; progress Braille spinner → static `⠿`; task-board renders only non-empty columns as equal-width cells; pipeline is a horizontal glyph-joined table with no scroll (showcase node counts are small); columns don't reflow on narrow. Everything else is lists and grids — email's home turf — and MUST render as a real component.
- **D6 — Fixtures frozen; tests clone the data_viz_test email pattern.** `ParityFixture.tree/0` gets NO fleet blocks; `email_golden.html` stays byte-identical (a per-slice gate: `git diff --exit-code` on it). Unlike #1830 (prose IS in the fixture, golden regen sanctioned), fleet is absent from the fixture — a golden diff this wave means a leaked edit. Each slice adds its own test file asserting: `_raw` kind, `assert html =~ "<table"`, `refute html =~ ~s(class="bp-)`, hex asserts equal to `StatusVocab.tones()["<tone>"]["light"]` / `email_skin` values. `tiers.ex`/`tiers_test.exs` untouched (all 14 types already classified).
- **D7 — Ledger shape: adopt `gp-w4-email-components`, split into three published children.** gp-w4's criteria widened to the full 14-type surface; slice tasks carry merge-gated criteria the LEAD closes; builders stamp evidence and leave `in_progress` until merge. *Why:* the wave task pre-exists with the exact scope; children-of-the-wave-task is the rubric shape.
- **D8 — No "filed follow-on" closure claimed for nested theming.** No such bp task exists (explorer-verified); slice C extends the compose.ex:44–49 comment to state fleet is evergreen-nested by the same design.
