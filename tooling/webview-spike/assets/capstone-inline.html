Five lanes investigated the wish against origin/main and the live guerrilla server. This report is their synthesis and their court: it tells the whole story, weaves the strongest evidence into one argument, rules the forks the lanes left open, and ends with an honest go/no-go. The verdict up front: GO — as a staged Sweet Spot on Expo/React Native, because the investigation's central discovery is that the system was accidentally built for this app. The epic's first commit is closer to a transcription than an invention, with exactly one hard server build and one deliberate exception.

01 · The grand view

What the investigation established

The wish reads like a product brief; the investigation turned it into physics. Barkpark Tasks is a hybrid of the chat app and the task app, exclusive to Barkpark Cloud at the start (interview truth: Cloud auth is the front door and identity layer; any Barkpark server is reached through it). Five lanes each took one decision the epic cannot dodge — what to build (product-shapes), how identity flows (identity-cascade), which shell and cache (shell-and-cache), how chat works on the wire (chat-third-client), and how tasks and papers read (tasks-papers-reading) — and each returned with the same central discovery from a different direction: all three surfaces are PortableDoc surfaces, and every surface the app needs already has a live, multi-client server heart. Task briefs are PortableDoc envelopes (docs/setup/TASK-SYSTEM.md:45). Chat messages persist server-rendered blocks beside source_markdown (chat charter D8). Papers are PortableDoc natively. The Go TUI is the existence proof that one renderer composed with the task API and the chat API yields excellence at all three surfaces at once — the mobile app is structurally the fourth instance of a composition the platform has already proven, after the TUI, Studio, and the web reader.

The second discovery is just as load-bearing: the server's client doctrine is accidentally mobile-first. Chat live deltas are ephemeral by design, settled truth is Postgres rows with a monotonic seq, and the documented recovery is reconnect-and-refetch-at-turn-boundary (chat_controller.ex:53-60) — which is exactly the architecture an app that gets backgrounded every thirty seconds needs. Tasks expose a pull keyset events feed (GET /v1/tasks/events?since → {events, cursor, has_more}) that is strictly better for phones than SSE iOS would suspend: cache the cursor, replay on foreground. One type-agnostic SSE stream per dataset (/v1/data/listen/:dataset) invalidates papers AND tasks together. Cross-device draft continuity already exists (D14: PATCH draft/mode/model on leave, re-GET on resume) — a draft typed on the phone resumes in the desktop TUI with no new server work. Nothing about mobile requires inventing sync.

And the third: the gaps are few, named, and sharp. Exactly one server capability is missing for the whole v1 read-and-chat floor — no path today turns a Cloud identity into a portable, per-user data-plane token that a plain team member can hold (verified from both the Cloud and the instance side by three lanes independently). Exactly one genuinely new backend subsystem is wanted — native push, where the repo greps clean for APNs/FCM. And exactly one honest contradiction must be ruled — the eventual-editing ambition structurally exceeds every non-admin token today. Everything else in this report is assembly, with file:line anchors.

02 · The verdict

GO — the Operator's Leash, staged through the Minimal

The recommendation, in one paragraph Build it. Ship v1 as a Reader-Communicator with teeth: the full login cascade with one-option auto-select and last-location memory riding the ratified bp-login-ux device flow; read-first tasks on the TUI's proven spine + criteria-first grammar, plus fence-free human triage (stage / relabel / move / papers-link — the server itself says “thought is not contended work”); the full chat floor (send / stream / interrupt / approve-deny, queued badge, D14 draft continuity); a premium cached paper reader; one universal search box over tasks + papers; and needs-you push notifications promoted INTO v1 as the single deliberate new-backend exception — three lanes independently converged on the lock-screen approval as THE reason a mobile app should exist, and shipping without it would ship an app without its killer moment. One hard server build unlocks everything: the member-reachable app-token exchange. If push slips, v1 ships as the pure Minimal and push becomes v1.1 — the staging is the safety net, not a compromise.

Why GO rather than go-differently: every alternative shape was seriously developed and lost on evidence, not taste. The Maximal (“Pocket Studio”) fails v1 because three of its pillars are not “just a client” — native push has zero existing machinery, paper block editing exceeds every non-admin token, and nine ChatLive surfaces are LiveView-only and reach no client today; it remains the honest v3 horizon. The pure Minimal fails the wish's own name — an app called Barkpark Tasks that can only read is a viewer, not a leash. The Sweet Spot is a genuine synthesis, not a midpoint: the Minimal's reading excellence plus the one thing a phone is for — being reachable when your agents need you. And the staging is honest: v1.5 adds the task verbs (claim / release / close-with-evidence as an explicit work mode), the needs-you inbox, and rich question answers when the filed /answer route ships; v2 adds prose-only paper editing behind the declared auth seam, task creation, and host/provider controls.

The mobile app is not a new product surface. It is the fourth client of machinery that already ships — one renderer, two protocols, and a login flow that already exists.

What makes this epic unusually cheap for its ambition: the interaction grammars transfer wholesale. The task spine ordering, fold rows, criteria-first conditional detail, and color-as-state-only are shipped TUI law; the Studio board's own evolution already reached the phone — wave 18's deck replaced kanban with a rail of literal 9:19.5 phone-frame cards, live on main today. The chat client discipline is codified in numbered decisions (D5 cursor ownership, D8 settle-at-result, D11 interrupt wedge, D12 client-local queued badge, D14 continuity) that transliterate to touch. The login cascade's n==1 auto-select fast path is ratified charter decision 19, already merged for the CLI wizard. Mobile is the fourth consumer of all of it.

04 · The spine

Login and the cascade: one hinge, then a port

The wish's spine — Cloud login → select server → workspace → project → dataset, auto-selecting the only option at every level and remembering the last — is not an invention. It is a port. The RFC-8628 device flow is shipped and mobile-ready as-is: start/poll are unauthenticated but rate-limited, TTL 600 s, poll interval 5 s, and the session is minted AT POLL after atomically consuming the approved row (device_auth.ex:29-43, 219-257) — the token never touches the browser. The CLI already auto-connects a single-Barkpark fleet with no prompt (setup_cloud_login.go:142-146, ratified as bp-login-ux decision 19's n==1 fast path) and persists server/workspace/project/dataset plus a most-recent-first known-servers list (config.go:29-58). The phone replicates that state machine over Keychain/Keystore. Below Cloud, auto-select is entirely client-side — workspace/project/dataset rows are bare {id, slug, name}; the one real server hint is that the default-slug project sorts first (tenancy.ex:858-869). Datasets have no production-first equivalent (tenancy.ex:1045-1047) — a two-line courtesy the epic should add in passing.

The one hinge: a two-endpoint token exchange Today's credential map dead-ends for a plain member from every direction: credentials reveal is team-admin-only and yields a root admin token the CLI itself refuses to store client-side; studio-link is member-reachable but consumes into a browser cookie with a Default-workspace OWNER grant — not a portable bearer; the bootstrap token is admin-gated and frozen at provision time; the chat-token mint is the right shape behind the wrong gate (instance owner/admin); Cloud PATs are structurally invisible to 68 of 74 gated Cloud routes (require_user only queries session rows, accounts.ex:548-570). The fix is small and precedented: Cloud POST /v1/barkparks/:id/app-token (user-session-authed, any team member) uses the registry's stored admin token server-side — the proven studio-link pattern, the admin token never travels — to call a NEW instance endpoint POST /v1/auth/app-tokens, which JIT-provisions the Cloud user by email via the idempotent Sso.find_or_create_user (sso.ex:69-80), grants MEMBER through create_membership/4 — the codebase's single Membership insertion point (tenancy/auth.ex:84-101), and the SSO/SCIM role precedent, explicitly NOT studio-link's OWNER — and mints a per-user, workspace-bound api_token with expires_at. Everything the mint needs already exists: expiry and revocation are enforced in the verify WHERE clause (auth.ex:44-53), and RequireChatAccess already honors a workspace token whose permissions include chat (require_chat_access.ex:55-58). Refresh is silent re-mint through the still-valid 30-day Cloud session. Lifetime is policy, not schema work.

05 · The shell bet

Expo/React Native — and cache-for-instant-open

The interview left the shell genuinely open; the evidence closed it. Three load-bearing discoveries make Expo/React Native nearly a transcription: (1) @barkpark/core is runtime-agnostic and injectable — its SSE transport deliberately avoids EventSource (which cannot carry Authorization) in favor of fetch + ReadableStream with Last-Event-ID resume; createClient({ fetch: expoFetch }) through the existing config.fetch hook (types.ts:114) plus a URL polyfill and a Hermes TextDecoder polyfill runs the whole ~21 KB typed client unmodified — no RN SSE library exists or is needed. (2) The “does @barkpark/react run in React Native?” question dissolves: renderPortableDocument() is a framework-free string emitter, byte-parity proven against the Elixir golden for 42 non-plugin types, skinned by one stylesheet (paper-surface.css, 80,451 B, all 18 once-unstyled families now covered on origin/main via PR #5651 with a compose-time coverage gate from #5656). A full-screen react-native-webview owning its own scroll, loaded via file/baseUrl — dodging both known Android traps by construction — inherits 66 of the 82-type union for free. (3) The server already prescribes the mobile lifecycle, as §01 established. PWA is refuted for v1 on four independently sufficient grounds: iOS storage is heuristic best-effort, not contractual — the wish's “instant open, remember where I was” promise would be conditional; Web Push is install-only with no silent push; SSE and all JS die seconds after backgrounding; and — found by this run — /v1/chat/* and /v1/tasks/* have NO per-app CORS knob, only a blunt instance-wide env var (DatasetCors covers /v1/data shapes only). Native Swift/Kotlin is refuted more simply: zero reuse of the typed client, the renderer, or the parity harness — everything rebuilt, forever drifting.

06 · Chat, excellently

The third sibling client of an engine that is already multi-client

The interview pinned mobile chat precisely: the existing Barkpark chat-sessions surface brought to the phone beside the bp chat TUI and the Studio GUI. The entire core loop — list, create, send, stream, interrupt, approve, resume — rides the frozen /v1/chat HTTP+SSE contract with zero new Elixir, live-verified on guerrilla. The client inherits the TUI reducer doctrine wholesale because it is accidentally a perfect mobile-backgrounding architecture: parse only three live frame shapes (system.init, text_delta, result); everything else settles at the turn boundary via GET ?since=maxSeq plus SSE re-attach with Last-Event-ID=maxSeq. No sync engine, no local write queue, no conflict resolution — the server owns truth, the phone owns a cursor. The session list folds one life-of-process fleet SSE (snapshot/state/heartbeat/title, opaque epoch:seq cursor, 256-flip ring, degrade-to-snapshot) through a pure herd reducer, and GET /v1/chat/rollup drives the app badge (blocked > working > idle > unknown, byte-matched to the Go herdRank).

The excellence bar, ruled: TUI-grade plus three cheap upgrades the TUI lacks — a context/headroom indicator derived client-side from persisted last_context_tokens/context_window (no server work), the compaction notice reproduced from the live frame, and a static thinking shimmer that resolves into the settled chat-thinking block. Of the nine LiveView-only ChatLive surfaces, the chat lane ruled each one reproduce/proxy/scope-out — the load-bearing scope-outs for v1: MCP entity chips (no PortableDoc block exists — a candidate epic-add that benefits the TUI too), the slash menu (native pickers instead), and the bypass-arm ceremony (bypassPermissions is unrepresentable over the transport anyway, a good constraint to inherit). The needs-you triple — approval / question / plan — is unified server-side and all three ride POST .../approval {request_id, decision: allow|deny}; D22 forbids caller-supplied updatedInput, so rich question answers wait for the already-designed /answer route (ct-bl-question-updatedinput, open) in v1.5.

The failure matrix was built for operators, not products Four distinct host failures collapse into one undifferentiated 503 {error: chat_unavailable} (chat_controller.ex ensure_and_send ~L249-253), and a host silently lost mid-turn produces up to 30 minutes of silence before the idle reaper emits exit reason=idle_reaped (recorder.ex:29). A phone user WILL hit this before a terminal operator does. v1 ships a client-side turn timeout (30-60 s of frame silence → an honest ‘agent unreachable’ state), and the epic files the small server fix splitting the 503 into reason codes. Also live reality: all 38 guerrilla sessions are provider=claude, execution_target=managed — codex and registered_host are modeled but unexercised, so v1 treats them as render-tolerated, not feature-complete; and on a server with no managed runtime the chat tab needs the onboarding empty state no sibling surface has designed.

Push, decided (ruling 3): needs-you push ships in v1 as a Cloud-held APNs/FCM relay keyed off the instance's chat_blocked webhook / Notifier source (herd charter D57h/D58h — keyed on pending-ask rows, never agent_state), deep-linking straight into the transcript's approval card. For a Cloud-exclusive app, one Cloud push identity beats teaching every self-hosted instance to hold push certs. This is the app's only genuinely new distributed system — 100% greenfield (the repo greps clean for APNs/FCM; scc-w13-notify-channels is Web Push + webhook only) — and it is architected to be severable: if it slips, v1 ships without it and nothing else moves.

07 · Tasks and papers, excellently

Two document-shaped surfaces on one read spine

Tasks and papers share the same content API, the same invalidation stream, and the same PortableDoc payloads — which is why they are one section here. The read spine, every box live today: the app cold-starts from its cache, repaints from GET /v1/tasks/prime?view=brief (built as one-call agent rehydration — my claims + ready head + recent events + lifecycle counts, ≤5 KB; a phone cold-start is the same problem, already solved), catches up through the events keyset cursor, and stays live over the per-dataset SSE stream that carries ALL document types — one stream invalidates both surfaces. Task detail is a presentation-grade PortableDoc brief rendered criteria-first (shipped TUI law, detail_render.go D15); the deck's 9:19.5 phone-frame cards (the Studio board's default view since wave 18) are the ready-made card language. Human-grade triage — stage, relabel, move, papers-link — is fence-free by the server's own design and needs only a valid token; that is what a human does on a phone. Agent-grade claim/stamp/close (epoch CAS, 2,700 s leases) waits for the v1.5 work mode.

The pagination law — state it in the epic brief as law GET /v1/tasks default order is desc(updated_at), desc(id) — UNSTABLE under live mutation on a 3,400+ task ledger: offset paging skips and duplicates whenever any row is touched mid-walk, and no client has ever actually paged (the TUI pulls limit=1000 and confesses truncation, fetch.go:38-41). Mobile must never bulk-sync the default order. Page the stable orders that already exist (parent= uses asc(inserted_at), asc(id); /ready uses priority asc, inserted_at asc, id asc) or ride prime + events. A recency keyset cursor over (updated_at, id) is a genuine, optional server epic-add — only if prime + events proves insufficient.

11 · Risks, unknowns, judgment calls

What could hurt, what we don't know, what only the user can decide

Held risks — accepted into the recommendation, with mitigations (1) Push in v1 makes the first release depend on the one genuinely new backend build — mitigated by severability: v1 degrades to the Minimal and push becomes v1.1. (2) The WebView long-paper spike is a hard day-1 gate; its failure mode (native prose fast-path promoted to v1) roughly doubles renderer cost — budgeted as the plan's biggest cost fork, not discovered mid-epic. (3) The workspace chat token has NEVER had a first-party interactive client — the phone is its maiden voyage; wave 1 includes a scripted end-to-end smoke (mint → list → create → send → approve → resume) as a pure minted token against guerrilla. (4) The global device-start rate bucket would let a popular app DoS its own login fleet-wide — cch-w1-peer-ip-pin is scheduled in wave 1, not hoped about. (5) Mid-turn host loss means up to 30 minutes of silence — v1 ships the client turn timeout; the 503 reason-split is filed server work. (6) Chat-tab dead-on-arrival on servers without a managed runtime — the onboarding empty state is in v1 scope. (7) Token sprawl from per-workspace minting — managed by the app-token list/revoke surface. (8) Version skew: old or self-hosted instances lack the mint endpoint — capability detection + manual token paste everywhere, exactly as the CLI does. (9) find_or_create_user has a get-then-insert race under concurrent first logins — close with an upsert while in the file. (10) Expo SDK churn (the 56/57 ‘current’ discrepancy was unresolved at run time) — pin at epic start, budget one upgrade per quarter; external-physics citations (iOS PWA policy, App Store guidelines) re-verified at epic start, since policies move.

Known unknowns, named: corpus prevalence of the 15 JS-missing field-family types in production papers (one cheap query decides emitter-port vs placeholder); whether any production papers carry non-public media today (decides the signed-src urgency); the true @barkpark/react per-import bundle number (run pnpm size at epic start); body_html staleness policy for cached readers (no policy exists anywhere today — the blocks-JSON ruling sidesteps it for rendering but the refetch rule still needs writing); and the task dossier's purpose composite field evolving in a concurrent session — mobile renders dossier fields from schema/capabilities introspection, never hardcoding.

Judgment calls left explicitly to the user (1) RATIFY push-in-v1 — this report recommends yes; it is the one break in ‘new client only’ purity, and it is severable. (2) The token permission set — [read,write,chat] recommended (ruling 1); [read,chat] if you prefer least-privilege and accept re-minting when creation ships. (3) Home surface — three tabs + badges recommended for v1; overrule toward the needs-you inbox or chat-as-home if your taste differs, the evidence is neutral. (4) The chat excellence bar — TUI-grade + three upgrades recommended; raising it toward Studio-grade moves real client budget. (5) Whether the dataset level appears as a real cascade screen or lives only inside a scope switcher — auto-select hides it 99% of the time either way. (6) The editing schedule — the v2 seam is declared; pull it earlier only with eyes open about the auth boundary. (7) Whether to build the admin-token attach/rotate verb this epic (fixes the permanently-stuck no_admin_token instance class) or accept destructive re-adoption for now.

12 · The recommendation and the first wave

Go — and what wave 1 takes if it goes

The epic is founded the moment the user ratifies the rulings above. It should run as an epic cycle (epics always via bp-epic-cycle), and its first wave is chosen so that every subsequent wave builds on proven ground: the two highest-risk unknowns (the credential seam and the WebView spike) are retired first, the one prerequisite fix lands, and the skeleton exists to hang everything else on. A considering-state epic candidate is already filed on the ledger — the live view below tracks the funnel from this paper.

W1·1
The token exchange, end to end. Cloud POST /v1/barkparks/:id/app-token + instance POST /v1/auth/app-tokens (JIT MEMBER, workspace-bound [read,write,chat], expires_at) + the app-token list/revoke surface — proven by a scripted smoke running mint → cascade walk → tasks prime → paper read → chat send/approve/resume as the minted token against guerrilla. This is the epic's security hot spot; it gets the cross-tenant negative tests and the security review.
W1·2
The WebView spike on real Android hardware. Cold-load + frame budget on a ~100-block paper with the real 80 KB stylesheet, memory with 3-4 warm WebViews, inline vs file/baseUrl delta. Pass → the renderer bet hardens as ruled. Fail → the native prose fast-path promotes to v1 and the renderer budget re-plans BEFORE screens are built against the wrong bet.
W1·3
The Expo skeleton. apps/mobile with the device flow + cascade + auto-select + MRU memory (port of setup_cloud_login.go + config.go semantics), MMKV/SQLite cache layer, @barkpark/core wired through expoFetch with the two polyfills, three stub tabs painting from cache, CI mobile lane. The skeleton is the proof the shell bet composes.
W1·4
The rate-limit prerequisite. cch-w1-peer-ip-pin: real peer-IP keying for the device-start bucket (limiter + Caddy forwarding). Without it, a wide rollout DoSes its own front door.
W1·5
The push-relay design decision. The Cloud APNs/FCM relay worker + device-token registry, keyed off the chat_blocked webhook — designed and spiked in wave 1, built in wave 2, severable throughout. Deep link lands on the transcript's approval card.
W1·6
The small unblocks. D36: tier_for_token learns chat (+ flip the test pin) so the manifest-driven client can discover its own noun; declare fields= on search.query; the 2-line production-first dataset ordering; the herd.go title-frame fold; file the 503 reason-split and the /answer adoption as v1.5 tickets.
No tasks yet.

Done, for the epic's founding wave, means: a plain team member on a phone-shaped client logs in through Cloud, lands in the right dataset without choosing anything they didn't have to, and reads live tasks, chats with a live session, and reads a real paper — all as themselves, on a token no admin had to hand them. Everything after that is excellence work on a proven spine.
