Guard the READ side of the cache-tag contract against bare-string iteration — the same hazard `revalidateBarkpark` already guards on the write side.

`barkparkFetch` built its Next `next.tags` array with `const userTags = opts.tags ?? []` and then SPREAD it. `opts.tags` / `opts.syncTags` are typed `readonly string[]`, but the type closes nothing: excess-property checks fire only on a fresh object literal, and this package ships CJS/ESM consumable from plain JS where no type exists at all. A bare **string** is iterable, so `tags: 'my-tag'` spread into `['m','y','-','t','a','g']` — and the per-element `typeof t === 'string'` filter downstream is exactly what made it silent, since every character passes it. The fetch was then cached under six single-character junk tags and never under the real one, so `revalidateTag('my-tag')` never matched: a permanently stale page with no error anywhere. A non-array non-string (a number/object from a config-assembled options bag) reached the spread and threw a raw `TypeError: not iterable` out of `barkparkFetch`, escaping the Barkpark error taxonomy. Both fields now go through a coercion: a string becomes a one-element list, an empty string and any other non-array are ignored — matching `normalizeFieldList`'s existing `string | string[]` coercion in the same module and the write side's "a non-array is simply ignored" posture. Callers passing arrays are unaffected.

`buildCspPolicy` had the same shape in `options.additional`: a bare-string value (`{ 'script-src': "'unsafe-inline'" }`) was walked character by character, so the `FORBIDDEN_SCRIPT_SOURCES` throw compared single characters against the forbidden list and NEVER FIRED, and the merge loop appended `'`, `u`, `n`, `s`… as separate sources. The emitted policy was not actually weaker — a single character is not a valid CSP source expression, so browsers drop it — so this was a **failed control, not an open hole**. It still mattered: the module's own note justifies that runtime check by saying the package "ships CJS/ESM consumable from plain JS, where no type exists at all", and the check was defeated in precisely that scenario. All three `additional` read sites now coerce, so `'unsafe-inline'` passed as a bare string throws as documented and a legitimate bare-string widening (`{ 'img-src': 'https:' }`) lands as one source instead of five characters.
