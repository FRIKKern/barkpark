`revalidate`: type-guard the `path` / `paths` arms of `revalidateBarkpark`. `paths` was behind a bare truthy check, and a bare string is truthy AND iterable — so a webhook body carrying `paths: '/blog'` made the `for...of` walk it character by character, firing `revalidatePath('/')`, `('b')`, `('l')`, `('o')`, `('g')` and never revalidating the intended path. This is the exact hazard the same function already documents on `sync_tags` ("a bare STRING is truthy and iterable, so a truthy-guarded for...of would walk it CHARACTER by character"), a ruling that reached `sync_tags`, `ids` and `types` but not `paths`. It bites harder here than where it was written: these are `revalidatePath` calls, not tag adds, and a single character is not a valid Next route path — so depending on the Next version it either mis-invalidates silently or throws out of the consumer's webhook handler, after the tag fan-out has already fired. `paths` is now `Array.isArray`-guarded with non-empty-string entries, and the single `path` arm is type-guarded the same way (a number or object from a raw `req.json()` body previously reached `revalidatePath` untouched). The `BARKPARK_ALLOW_ALL_REVALIDATE` gate is unchanged and still keys on presence, not shape, so a caller without the opt-in is refused whatever they sent.
