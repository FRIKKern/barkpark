Three fixes to the server read path and the Server Actions bundle.

**`fetchOptions.timeout` is now actually armed.** It was a declared-only option: the type documented it under "Per-call defaults applied by `barkparkFetch`", and its only read was inside the timeout error's own constructor — there was no `AbortController`, no `AbortSignal.timeout` and no timer anywhere on the server fetch path. A consumer who set `fetchOptions: { timeout: 5000 }` got no timeout at all, so a hung Barkpark origin held the Server Component render until the hosting platform's own limit and `BarkparkTimeoutError` was never raised. A declared option nothing arms is worse than an absent one: the consumer relies on a promise the code never makes. The deadline now bounds the whole read — the draft 401-reissue retry and the response-body read included, so a server that streams headers and then stalls the body cannot outlive it — and composes with a caller-supplied `signal`, so either can abort and the winner stays attributable: a caller cancellation still surfaces as a plain `AbortError`, our deadline reports its own window, and a caller's `AbortSignal.timeout` no longer reports the config's unrelated window as `timeoutMs`. There is still no default: omit `timeout` (or pass `0`) and the read stays unbounded, exactly as before.

**`createDoc` no longer crashes on a `_type` that names something on `Object.prototype`.** The schema lookup was a prototype-chain read on a plain codegen object literal, and `_type` is reachable from untyped form/JSON input, so `createDoc({_type: 'toString', …})` resolved an inherited value whose `.parse` is not a function and threw a raw `TypeError` out of a Server Action — escaping the Barkpark error taxonomy. This was a crash, not a validation bypass: no inherited value carries a callable `.parse`, so nothing was ever validated and waved through. The lookup is own-key only now, which makes an inherited name behave like any other unregistered type. An own key whose value is not a usable schema is refused loudly with a `BarkparkValidationError` instead — silently skipping validation there would have turned a codegen bug into a real bypass.

**An `id` or `type` of `..` no longer retargets the fetch.** `encodeURIComponent` escapes `/` but not `.`, so `id: '..'` reached `fetch` intact and the URL parser resolved `/v1/data/doc/production/post/..` to `/v1/data/doc/production/` before the request left. Bounded — the API declares no route there, so the retarget 404s and nothing over-broad was ever read — but it produced a `BarkparkNotFoundError` naming a URL the caller never asked for, and a Next data-cache entry tagged `<prefix>:doc:..` that no `revalidateTag` could ever match. Both segments are now checked against the same rule `@barkpark/core` applies to its own path builders.
