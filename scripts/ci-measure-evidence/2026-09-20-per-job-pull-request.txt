HOW TO RE-DERIVE THIS FILE, exactly:

    bash scripts/ci-measure.sh --per-job --runs 50 --pages 10 --raw-out raw.ndjson
    bash scripts/ci-measure.sh --per-job --raw-in raw.ndjson      # no network

WHAT IT IS. Every minute below is STEP-DERIVED: a job's compute is the span of
its executed steps, so a job with zero executed steps contributed ZERO whatever
its wall clock said (the rule at the top of scripts/ci-measure.sh, and the
reason the first diet table was wrong). Cancelled and zero-step jobs are COUNTED
in their own columns and are never summed into any minute column. The
`skip` column is jobs an `if:` declined; those render a check run and cost
nothing.

WHAT IT IS NOT. It is not a run rollup. Every conclusion here comes from
`actions/runs/<id>/jobs`; `.conclusion` is deliberately absent from the run-list
projection, so there is nothing for `continue-on-error` to launder. Adjudicated
in .github/run-level-readers.allow (scripts/ci-measure.sh, 21 refs, JOB-LEVEL).

IT IS NOT A SAMPLE EITHER, and it is not scaled: inside the stated window every
completed pull_request run of each workflow is walked, up to the 50-run cap, so
the medians are real medians. What bounds it is the window the feed reaches —
10 pages is GitHub's own 1000-item ceiling, not a choice. A workflow with fewer
than 50 runs in the window is reported at its true, smaller n, and n is the
`execs` column.

THE SORT IS execs x median, NOT median. A 15-minute job that fires twice is not
the diet target; a 2.58-minute job that fires on 25 of 49 pushes is.

THE PROPERTY THAT MAKES IT SAFE TO MOVE. It reads no source. Both its oracles
(`mix deps.audit` and `scripts/hex-audit-oracle.sh`) resolve LOCKFILES against
an advisory database. An `api/lib/*.ex` edit cannot change what they say. The
new gate is the set of files that can: api/mix.lock, api/mix.exs, cloud/mix.lock,
cloud/mix.exs, .github/hex-audit-baseline.txt, .github/workflows/security.yml,
scripts/hex-audit-oracle.sh, scripts/main-red-breaker.sh, scripts/breaker-capture.sh,
scripts/run-instrument.sh.

AND IT IS NOT REQUIRED. The four contexts branch protection enforces on main are
Cloud gate, Console gate, Elixir gate, PR references an active task
(.github/required-checks.json, protection.required_status_checks.checks). This
job is none of them, is not in any required aggregator's needs:, and its own
comment says so ("nothing here is a merge gate"). It is an S6 exclusion.

THE COVERAGE THAT IS NOT LOST. security.yml's `push: branches:[main]` arm is
paths-filtered on api/**, and the dispatcher emits api=true AND locks=true
unconditionally for any non-pull_request event. So every merge that touches api/
still runs the full CVE audit on main, at the same granularity as before. What
stops is re-asking the question on each PR push whose diff cannot change the
answer. (The answer CAN change with no diff at all — a new upstream advisory —
but that is a clock, not a diff, and the per-PR path never caught it either.)

WHY A JOB-LEVEL `if:` AND NOT A WORKFLOW-LEVEL `paths:`. A paths-filtered
workflow publishes NO run and NO check run, which makes every name in the file
ABSENT; a required context that is absent can never go green and the PR blocks
forever. A job-level `if:` inside a running workflow still renders the check run,
with conclusion `skipped`. security.yml carries THREE required-adjacent names and
its own header forbids a pull_request paths: key outright. Nothing in this change
adds or widens any paths: key.

  the API on a post-merge head, and criterion 2 of the row says so.

────────────────────────────────────────────────────────────────────────────
WHAT THE CHECK-RUN COUNT DOES **NOT** DO, stated because the row asks for it
────────────────────────────────────────────────────────────────────────────

The umbrella's c1 wants "check runs per PR push under 20". A JOB-level `if:`
CANNOT lower that number: a skipped job still renders its check run. 64 distinct
names before, 64 after — by design, and the design is the deadlock rule. The two
halves of the mandate pull against each other, and this change buys the minutes,
not the count. Lowering the COUNT means removing NAMES, which for a non-required
name is a workflow-level paths: filter — the one instrument this task forbids.
That tension is a finding, not an omission; it is reported rather than papered
over with a number that would have to be the count of something else.
