[2 · heading]
The Wave Deck — the epic cycle as an
interactive, slide-by-slide experience

[3 · byline]
One wave, one deck
5 decision gates
Live fleet, live ledger

[4 · ingress]
The 7-phase epic cycle already
externalizes everything it knows into
Barkpark — a living wave Paper, a
published task ledger, a
wave_status
heartbeat. The Wave Deck renders that
state as slides a human can ride: watch
the fleet fly in realtime, see exactly
what was checked and what wasn't, and
DECIDE at five gates whether to research
more, build, or land. This paper is the
information spec: slide by slide, what
each screen must inform, what is live,
where the data already lives, and what
is genuinely open for design.

[5 · callout]
What this paper is (and isn't)
This is the
what-to-inform
spec for Claude design — content, data
sources, decision moments, live
elements. It deliberately says nothing
about visual style, layout, or component
aesthetics. Every slide below states its
job in one line; if a slide can't, it
shouldn't exist.

Job:

Slide 3 — Fleet in Flight (Survey, live)

[25 · paragraph]
Job:
the realtime spectacle with substance —
you SEE 5–20 minds working, and each one

rides the existing Studio chat surface:
the wave is a chat session; the fleet is

Per-agent card (the unit of this slide):

[27 · list]
assignment key + the question, one line
(
survey:auth-seams
)
model tier badge (Sonnet/Opus/Fable) —
the user asked to SEE the amount and

[28 · callout]
Realtime contract
Liveness comes from two independent
feeds and the deck must survive either
going quiet: (1) the chat/workflow
stream — agent spawn, phase change, tool
activity, tokens; (2) the bp ledger —
heartbeat, task stamps, Paper sections,
which persist. Stream dies → deck
degrades to polling bp and says so.
Never render a frozen “live” view as if
it were current.

[29 · paragraph]
Data:
workflow phase groups + agent labels
(spawn/complete events); Studio chat
SESSIONS surface (agents rail, per-agent
drill-down transcripts); tokens/elapsed
from the run.

[31 · heading]
Slide 4 — The Coverage Map (Survey
results)

[32 · paragraph]
Job:
make the EDGES of knowledge visible —
this slide is the honest heart of the
deck and the evidence base for Gate 1.
Not “what did we learn” but “what did we
check, what did we find, what did we
check and NOT find, and where did nobody
look”.

[33 · list]
Checked & found
— path, what it was checked for, the
one-line takeaway.
Checked & NOT found
— rendered as loudly as found. “No
existing rate limiter in api/” is a
decision-in-waiting, not a footnote.
Partial
— ran out of timebox; candidates for the
verify round.
Unreached corners
— named by the Digest; unlisted =
unchecked is the rule, so the map must
admit its own blank space.
Open questions
— every surveyor's parked unknowns,
deduped.

[34 · paragraph]
Aggregations that matter:
N files checked across M surveyors ·
found/not-found/partial ratio · which
repo areas got zero coverage. A heatmap
over repo areas is a natural fit; the
raw per-file table must stay one tap
away — trust comes from the ability to
drill to the specific file and claim.

[35 · paragraph]
Data:
surveyors' structured
coverage[]
({path, checked_for,
found|not_found|partial, note}), folded
into wave Paper §Survey digest by the
Digest phase.

[38 · paragraph]
Job:

Must inform before the user can decide:

[40 · list]
what is now established (with the
coverage map one slide back)
where survey reports contradict each

sides
what remains unknown that Decide cannot
live without — the justification for

the proposed verify fleet: per
assignment its question, model (Sonnet

[41 · cards]
Research more ↺
Add or edit survey questions (user can
type their own); another cheap Sonnet
round flies; the Paper and coverage map
grow — never fork.
Verify →
Approve the fleet as designed (default).
User may strike or add assignments and
flip a Sonnet↔Opus choice before launch.
Skip ahead ⏩
“I already know enough.” Deck names the
claims that will go unproven; the choice
is logged into the Paper with a dated
note.

[55 · heading]
Slide 8 — The Plan & GATE 3: approve the
wave

[56 · paragraph]
Job:
the biggest decision on the deck:
exactly what will be built, by which
class of mind, proven by what. Nothing
here is hypothetical — every slice IS a
published bp task the user can open.

[57 · list]
Decisions
— each with its one-line why; where
verification overturned the original
direction, show the reversal explicitly
(before → after).
Slice cards = task cards:
title · bp task id (live link) · surface
· builder model badge (Opus =
well-specified; Fable =
subtle/high-blast-radius — the badge
carries the architect's reasoning on
hover/tap) · the exact gate command ·
acceptance criteria with their
merge-gated ones marked.
Backlog seeded
— discovered-but-deferred tasks filed
now; the ledger shows the future, render
it.
Fleet preview
— N builders about to fly, model mix,
expected file-overlap = zero (slices are
worktree-isolated by design).

[58 · cards]
Build →
Fire the builders (default). The Paper
already carries the plan; the heartbeat
flips to “building N slices”.
Trim / retarget
Strike slices (their tasks stay filed,
unclaimed, honest in the backlog) or
demote/promote a builder model; then
fire.
Redirect ↺
The plan is wrong at the root — send it
back to Digest with a note. Expensive
and rare; the note becomes lead_notes
for the re-run.

[84 · callout]
The one honest engineering note
Today the 7 phases run as ONE background
workflow. Real gates need the run to
pause on user input. The clean cut: the
workflow already externalizes ALL state
into Paper + tasks at every Fable
boundary — exactly where the gates sit.
So gates = run the cycle as phase
segments the lead fires one at a time
(the deck's gate answer is the lead's
cue), or a workflow-level pause
primitive if one lands later. No phase
needs to change what it writes.

[86 · heading]
Interaction doctrine

[87 · notes]
Every gate has a default and (in auto)
zero-wait pass-through. The deck adds
decision power without taxing the user
who trusts the loop.
D1
Gates are optional; auto mode is today's
behavior.
“Research more” costs Sonnet-minutes.
The deck shows the cost of each option
AT the gate, so choosing more research
feels safe, not indulgent.
D2
Research loops are cheap by design.
Every extra round appends to the same
wave Paper. The deck is a lens on the
Paper — rewind any wave by scrolling it.
D3
Loops grow one Paper; they never fork.
Choice, author, note, timestamp —
appended to the Paper. The wave's story
includes the human's decisions, not just
the agents'.
D4
Every gate answer is recorded.
Every gate is judged against it.
Persistent, verbatim, untruncated.
D5
The wish never leaves the screen.

[89 · heading]
Principles the design must carry

[90 · notes]
Absence of prior art, a refuted premise,
an unreached corner — these change
plans. Never render them smaller than
positives.
P1
Not-found is as loud as found.
The Paper states the plan before each
fleet flies; the deck must too. A
mid-wave visitor orients in one glance.
P2
Always show what is in flight.
“14 agents” is a number; 14 cards with
model badges, states, and assignments is
a fleet. Aggregate AND enumerate.
P3
Counts with faces.
Grade travels with commentary; pass
travels with the output that produced
it; count travels with the list behind
it.
P4
Never a bare number.
Agents die, gates go red, streams drop,
builders stall. Each is a designed
state, not an edge case —
loading/empty/error at the Kinsta/Vercel
bar.
P5
Honest states everywhere.
Every aggregate opens to its evidence:
coverage cell → file+claim, proof row →
full output, slice card → bp task, agent
card → transcript.
P6
Drill-down is the trust mechanism.
Deck states mirror task design language
(open/claimed/in_progress/done, criteria
met/unmet) — no parallel status
taxonomy.
P7
One vocabulary with the ledger.

[92 · heading]
Open questions for Claude design

[93 · list]
Deck vs scroll: are slides discrete
steps (carousel with the loop map as
navigator) or sections of one scrollable
live document? The Paper is a scroll;
the gates argue for steps.
Where do gate timeouts land — how long
does a soft gate wait in attended mode
before auto-defaulting, and how is that
countdown shown?
Fleet view at 20 agents: cards, rows, or
a swarm visualization with
detail-on-hover? (80-col TUI parity
exists as a constraint worth respecting
— the deck should have a terminal
projection someday.)
How does the deck coexist with the raw
chat transcript — tabs, split, or the
deck AS the chat's rich rendering of a
wave-scoped session?
Multi-wave epics: does the deck show one
wave or the epic's wave history (Paper
per wave, charter as the spine)?
Notification surface for gates in
unattended mode — push, email, Studio
inbox (tickets exists), or all three?
