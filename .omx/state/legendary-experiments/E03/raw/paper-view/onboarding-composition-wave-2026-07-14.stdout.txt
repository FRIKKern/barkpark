Wave 1 landed grade A- (paper bp-onboarding-composition-wave-2026-07-13): the ONE-transaction ONE-receipt onboarding — nothing → authenticated → MCP-connected → correct-team instance → a proven read-only tool call, under 5 min, never printing the bearer. Strategic direction

The finished experience: a first-time Windows user, coming from Barkpark Cloud, runs bp once and the CLI knows who they are, which team they belong to, and which instance is that team's — with no phantom "-2" duplicate servers, no config bricked by a Notepad BOM, and a single bp whoami / doctor receipt that reads back the whole identity in one honest envelope. From the Cloud side, provisioning stamps BARKPARK_CLOUD_URL so Studio renders the "sign in via Cloud" button instead of a dead corner. Identity becomes composed and legible end-to-end, not scattered across URL-string keys.

The load-bearing reconciliation (surveyors must nail this first): the epic task's wave_status claims wave 1 built "8/8 slices" — but the local checkout / origin main shows internal/cli/config.go with no InstanceID, no Aliases, and no BOM strip; the ServerEntry is still keyed purely by normalized URL. This matches the KNOWN failure mode of wave 1 (Decide committed to a diverged LOCAL main and never PR'd — same reason the wave-1 charter is stranded on neither origin nor local). So wave 2 likely builds the identity PLUMBING fresh, not merely activates it. Every builder must diff its target files against origin/main before writing, and treat wave-1 "done" claims as unverified until proven.

Choices I lean toward (tentative — Decide finalizes after two explore rounds):

Key identity by InstanceID first, URL second. Add InstanceID string + Aliases []string to ServerEntry; key Remember/Find/IsActive/DisplayName by InstanceID when known, fall back to normalized-URL only for ID-less bare local dev. A second hostname of a known instance folds into Aliases, never mints a "-2". Source of truth for the ID: the control plane's DomainStatusResult.Instance.ID + Domains[] (already modeled in internal/cloudclient/client.go).

Wire the ID at connect/attach (task-e6b0bc97130bae89) — plumbing is inert until a caller stamps the real ID. This is the E2E activation: one instance via two hostnames → one ServerEntry.

BOM tolerance is a one-line strip (bytes.TrimPrefix(raw, []byte{0xEF,0xBB,0xBF})) before Unmarshal in LoadConfig; SaveConfig already emits BOM-free JSON and self-heals. Prove it with a failing-first test (TestBOMBricksLoadConfig flips to green).

whoami is the receipt spine. Extend bp whoami -o json (builtins.go) to carry instance_id + aliases[] + team + auth_tier + MCP catalog version/names + read-only call result + the exact client-reload instruction. The onboarding doctor composes over this — don't fork a second receipt.

Team model needs a real backend concept. bp teams / bp team use presuppose the server/control-plane models teams + memberships and can mint --team-scoped instance credentials. Whether that maps to existing tenancy/workspace scoping (bp cloud members, workspace-scoped tokens) is the biggest open design question — surveyors map it before Decide commits a shape.

BP-ONB-04 is a provisioning + Studio-render pair: stamp BARKPARK_CLOUD_URL at provision time (cloud/**) and make the Studio session view render the Cloud login button when it's present (session_controller.ex / session_html/new.html.heex). Backfill for existing instances is a separate backlog slice.

Prioritize: (1) origin-main truth reconciliation — everything downstream depends on whether we build or activate; (2) the ServerEntry identity core (BP-ONB-05/12) since 02/03/04 all read from it; (3) the team-model design question, because it's the one slice whose backend shape is genuinely uncertain.

Constraints held: Opus-only every phase (Fable exhausted, never Haiku). No charter file exists — reconstruct epic context from the epic task + wave-1 paper; Decide writes the charter FRESH and lands it via clean-extract (detached worktree off origin/main → copy charter → commit → PR → admin-merge), NEVER pushing diverged local main. Builders commit to LOCAL worktree branches and do NOT push; the steward pushes green branches.
