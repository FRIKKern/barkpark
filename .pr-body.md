## The green that measured the wrong thing

`bp whoami` and `bp doctor --onboarding` report a CLI-freshness leg. On the
release path that leg asked exactly one question:

    is cliVersion == the newest published cli-v* tag?

and answered `status: "up-to-date"`, `up_to_date: true` when it was. That answer
says nothing about whether the binary carries the CLI code, and when nobody cuts
a tag it never will. **Re-measured on `origin/main`, 2026-09-16:**

    $ git rev-list --count cli-v1.21.0..origin/main -- internal/cli
    181
    $ git diff --name-only cli-v1.21.0 origin/main -- internal/cli | wc -l
    301

`cli-v1.21.0` was cut 2026-09-03 — 13 days ago — and is still the newest
published release. So an operator who ran `bp upgrade` this morning holds a
binary 181 CLI commits behind the code, and every freshness surface tells them
they are up to date. (`scripts/cli-release-cadence-gate.sh`, the CI oracle, uses
the narrower `internal/cli/setup/assets` pathspec and reads 5 today; both
numbers are drift, and both are cleared only by a tag.)

This replaces the row's filed "352 commits behind" premise, which was a
staleness number inside a staleness row.

## What changed

`readCommitDrift` (the reading `cli_staleness.go` already took for dev builds —
build commit vs `origin/main` over `internal/cli`, pure local git) is split out
from its dev-build rendering, so a second caller can render the same facts with
a different remedy. `channelStaleness` is that caller, consulted in both
`whoamiCLIFreshness` and `onboardingCLIFreshness` **only on the leg that was
about to return up-to-date**:

    CHANNEL STALE — you run the newest published release (1.21.0) and it is
    behind the code: this bp was built from 67732cab5 (built …); origin/main is
    at f2d2666c6 with 301 changes under internal/cli/ it does not carry. cut the
    next cli-v<semver> tag — `bp upgrade` cannot clear this, because you already
    run the newest published release.

The remedy is deliberately **not** `bp upgrade`: in this state upgrading fetches
the same bytes back. That is the honest statement of who owes what.

This is keyed on the GAP, not on the release value — so it is live today and
goes permanently silent the moment a tag carrying the code is cut. It is not a
second min_cli surface: `internal/cli/min_cli_gate.go` (#18626) reports the
server-advertised floor at `bp capabilities`; this reports code drift at the
freshness leg. Neither blocks a command.

## Scope, stated rather than implied

The reading needs a checkout. A `curl | sh` stranger with no barkpark repo gets
`ok=false` and keeps the release-channel answer — `TestWhoami…MakesNoChannel
ClaimWithoutACommitStamp` pins exactly that, so the change cannot be read as
covering them. Reaching that population is the row's criterion c1 (a verdict
from OUTSIDE the binary), which is an `api/` seam and is not built here.

**Owner-blocked half:** cutting `cli-v1.22.0` is the only thing that makes the
channel fresh, and tagging is an owner action. Nothing in this PR cuts, pushes,
or requests a tag.
