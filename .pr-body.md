## The defect, measured

A task can exist twice — `x` (published spelling) and `drafts.x` (its draft twin).
Every other Barkpark display surface renders such a pair as ONE card. The TUI was
the last one that did not: `internal/taskboard` joins ACROSS twins by `bareID`
(`buildByBare`, `bareID`, `paperChipResolver`) but never dropped a row, so a
twinned pair painted two cards — routinely with DIVERGENT lifecycle.

Measured against a **real board cache on this box**
(`~/.config/barkpark/taskboard-cache-1b0feac98e580cdd.json`, 1306 tasks, 55 of
its rows a `drafts.<id>` whose bare twin is in the same snapshot), running
`BuildBoard` over it:

| | cards painted | bare ids painted under BOTH spellings | unpaired draft cards |
|---|---|---|---|
| before | 535 | **19** | 104 |
| after  | 481 | **0** | 104 |

Specimen `task-f74742b835867f8d` — **same title, two cards**, the published row
reading `in_progress` and its draft twin reading `open`. Before: published 2 /
draft **1**. After: published 2 / draft **0**.

CONTROL, `task-b97741617bf6c860`, an untwinned published row in the same
snapshot: published 2 / draft 0 **before and after**. Its count does not move,
so the vanished card is evidence about the twin, not about the probe. (Both
"2"s are the NOW-band + epic-header structural pair the counter deliberately
counts; it is identical on the twinned and untwinned rows.)

The ledger is not short of specimens: `bp export --type task --perspective drafts`
returns **352** bare ids holding both spellings.

Why the live `/v1/tasks` route did not show this: it already collapses
server-side (`Tasks.Query.collapse_twins/1`, called from
`TasksController.index/2`) — probed live, 6 `drafts.` rows in a 1000-row page,
all six **unpaired**. The twins reach the TUI through the seams the server does
not cover: the on-disk first-paint cache (above), `mergeForward`'s union of a
cached and a live snapshot, and any server predating `dr-w34-s4`. That is why
the collapse lands at `BuildBoard` — the one funnel every snapshot passes
through — and not in `fetch.go`, which a cache-restored snapshot never enters.

## The rule is mirrored, not re-spelled

The published-wins rule already exists three places on the Elixir side. The one
this surface can express is
`Barkpark.Tasks.TwinResolver.winning_spelling_tier/1`
(`api/lib/barkpark/tasks/twin_resolver.ex`) — *"bare-id rows when any exist, the
`drafts.` twins otherwise"* — the **spelling-only** tier that module defines
precisely for doors that, in its own words, "never split on `status`". The Go
`Task` envelope (`internal/taskboard/types.go`) carries no status field, so the
spelling tier is not a shortcut here, it is the only form of the rule available;
`collapseDraftTwins` is a line-for-line transcription of that four-line function
and its doc comment cites it by name.

**Why it is not shared mechanically:** the rule lives in Elixir and this reader
is Go, with no codegen path between them for logic (only wire keys are pinned),
so the transcription is the smallest possible one — a spelling predicate and a
"keep the bare tier" fold — and it is anchored by name at the Go call site so
`scripts/docs-anchors-check.sh`-style drift is visible to a grep for
`winning_spelling_tier`.

## The carve-out is kept

An **unpaired** `drafts.<id>` row — no bare twin in the snapshot — IS the row of
record and survives untouched (PDS-D748 item 2). That is every task born through
`/v1/data/mutate`: 104 of them still paint in the measurement above. This is
deliberately NOT a blanket `drafts.`-prefix drop, the form
`Tasks.Query.collapse_twins/1` refuses for the same reason.

## `bp task next --frontier` is NOT touched

`internal/cli/tasks_next_cmd.go` is unmodified — both `Perspective: "drafts"`
call sites (lines 77 and 312) are byte-identical to `origin/main`. PDS-D748 item
5 rules a flip to `"published"` a **REGRESSION**, and this PR does not make it.
The collapse is consistent with that ruling rather than an exception to it: the
Perspective decides what the CONTENT STORE returns (whether a never-published
document is visible at all), and the population it exists to keep reachable —
unpaired drafts — is exactly what the carve-out preserves.

## Goldens

**Zero goldens moved.** `internal/taskboard/testdata/{board,cluster,flat_queue,
tasks}_fixture.json` contain no `drafts.`-prefixed doc id at all, so no rendered
golden had a twin to collapse; the full `go test ./internal/...` is green with
every golden byte unchanged. (A fixture with no twinned pair cannot detect this
defect — which is why the new arms build their own.)

## The arms, proved by mutation

Four new tests in `board_test.go`, each proved discriminating by mutating the
implementation and observing the red, then restoring:

| mutation | collapse arm | unpaired arm | retarget arm | not-a-prefix-drop |
|---|---|---|---|---|
| **M1** collapse call removed (the revert) | **RED** | pass (quiet) | **RED** | pass |
| **M2** blanket `drafts.` drop (over-collapse) | **RED** | **RED** | pass | **RED** |
| **M3** parent retarget removed | pass | pass | **RED** | pass |

- `TestBuildBoardCollapsesDraftTwinPublishedWins` — **the test that FAILS if the
  collapse is removed.** A twinned fixture paints two cards again and it reds on
  "draft twin painted 1 card". It also pins that the SURVIVOR is the published
  row (it is the one reading `in_progress`, the draft read `open`) and that
  `TaskCount` counts the pair once.
- `TestBuildBoardKeepsUnpairedDraftTwin` — the **quiet** arm: green with AND
  without the collapse (M1), red only on over-collapse (M2). Carries the
  untwinned CONTROL row.
- `TestCollapseDraftTwinsRetargetsSuppressedParent` — the collapse may not
  manufacture an orphan: a child whose `parent_id` names the suppressed draft
  twin re-homes on the survivor.
- `TestCollapseDraftTwinsIsNotAPrefixDrop` — the unit pinned directly against
  `winning_spelling_tier/1`'s shape, plus order preservation and input
  non-mutation.
